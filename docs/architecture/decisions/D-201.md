- **D-201 (2026-10-12, deferrals part A: the Zenodo pin record; user-approved with the merge of part A).** A Zenodo pin records the version DOI, the
  record id (`record`, optional, must equal the DOI's), the version label (`version`, optional), the file name, its
  size (`bytes`/`size`) and its digests (`sha256`, required for an import; `md5` as the deposit's transport check).
  `--verify-against-pin` checks a local file offline: file name, size, MD5 when pinned, SHA-256
  (`raw.fetch.verify_download`; `raw.fetch.digest` on a mismatch, `raw.fetch.unverifiable` without a SHA-256). The
  working manifest's snapshot `pin` holds the whole record (git and listing pins keep their phase-6 projection).
  `--fetch` of a download pin of 100 MiB or more needs `--i-consent-to-large-download` (U-07), as `agentprov fetch`.
  - **Why:** the deposit is the origin; its record id and version identify it on Zenodo, its digest identifies the bytes.
  - **Rejected:** fetching the record's metadata to check the version label (network for every import; the label is a
    deposit claim, recorded as such); MD5 alone (the raw store and every AER artefact are SHA-256 addressed).
