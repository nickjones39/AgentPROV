- **D-935 (2026-10-28, engine-output PROV limits: a PROV-document JSON limit of 256 MiB, and a per-source prov/validate
  memory cap `[import] prov_rss_bytes`; user-approved 2026-10-28 in the wave-2 session, "Fix and re-import"; core byte
  class 1 (validation scope), byte-neutral; family byte class 1).** The wave-2 DTap import failed 10 executions on
  limits, not on mapping (F-12, read-only measurement through the queue):
  - DTap's PROV grows with the square of a run's model calls: each call `used` every message of its context (44,100
    statements for 210 calls, with 21,945 Inference-6 `wasInformedBy`), and the assessment bundle states one
    `apv:ExposedTo` and one `apv:PotentiallyInfluencedBy` per request part and untrusted context member (E.7.3; 21,945
    and 20,124). 168 calls give 68.7 MB, 210 give 103.1 MB, 778 give 996.5 MB.
  - Generation is cheap (401 MiB and 833 MiB peak for 134 and 210 calls); tier 4 (the PROV-O round trip) costs about
    80 x the PROV size (prov-perf's fit). 7 executions (134-157 calls, 38-64 MiB of PROV) passed the load and crossed the
    4 GiB prov cap in tier 4 (`worker.limit.rss`, reported for SEM and PROV of one job); 4 (168-210 calls, over 64 MiB)
    were refused at load by the raw-input JSON limit (`pv.prov_structure.not_json`).
  - **Decision.**
    - A stored PROV-JSON document is parsed under `ingest.limits.prov_document_limits` (`max_json_bytes` at least
      256 MiB; every other limit unchanged): the validator (`validate.prov`) and `CorpusReader.read_prov` (stats, package,
      inspect). Raw source input keeps 64 MiB.
    - `[import] prov_rss_bytes` (an integer from the prov cap, 4 GiB, to `RSS_CAP_CEILING`, checked at profile load)
      raises the source's `prov` and `validate` jobs' cap: `import` carries it on each prov job (`Job.limits`), `validate`
      reads it from the profile version the corpus records, and `recompute`/`derive` through the injected `Catalogues`
      (`worker_caps`). DTap declares 16 GiB (D-934's family commit), which covers tier 4 up to about 160 MiB of PROV.
  - **Bytes.** Limits enter no output: a test derives and validates the same logs with and without the cap and compares
    the PROV bytes. `validate/` is in the validation stage scope, so that digest moves; no stored corpus changes.
    Correction (2026-10-29): `ingest/limits.py`, where `prov_document_limits` lives, is in all four stage closures (aer,
    sem, prov, validation; `agentprov.stage_scopes`), so D-935 moved every stage's code digest, not only validation's.
    F-8 covers it: DTap was built at a commit holding D-935, and earlier corpora recompute at their own building commits.
  - **Not recovered.** One DTap execution (openclaw, 778 model calls) yields 996.5 MB of PROV (8.4 GB to generate) and
    would need about 76 GB for tier 4, far above the worker ceiling. It stays failed and is documented as a size limit,
    not an outcome exclusion. The real fix is an O(n) representation of context membership (incremental context
    collections) and of exposure pairs: a v0.2 PROV design item.
  - **Addendum (2026-10-28, the DTap re-import at 1adb6b36).** The other nine executions D-935 targeted (38-76 MB of
    PROV) fit and are recovered. Two did not complete in the 16-worker import:
    - openclaw, 778 model calls: it now fails on the output-frame limit (`worker.limit.output`) before its memory, at
      any load. It is the corpus's one registered failed execution: its AER record is released, it has no PROV, and it
      is counted and disclosed (datasheet item 24). Nothing is excluded by outcome.
    - openaisdk / gpt-5.1, 210 model calls, 103.1 MB of PROV: the 16 GiB cap holds its memory, but its prov job needs
      about the worker's full per-job CPU budget (`WorkerLimits.cpu_s` = 300 s), and it stopped on `worker.limit.cpu`
      under the 16-worker import.
  - **Addendum (2026-10-29, the retry; user decision 2026-10-29: retry just that run on a quiet machine).**
    `import --retry-failed` into the same tree at the same building commit, with the machine otherwise idle, derived the
    210-call execution: its PROV, SEM and validation are `ok`. The 778-call run failed again on the output limit.
    `validate --jobs 16` then passed 67,710 of 67,711 (the 778-call run is the one failure) and `verify --level chain`
    passed. The recompute dry run reproduced all 67,711 executions but found 2 register rows the retry had written
    wrongly (the judge files of the two pinned LFS trajectories called unused; D-981, fixed in the importer). The
    corpus that passed is therefore `dtap-bench-w2c`, the `recompute --out` version of w2b at the same building commit
    (1adb6b36; user decision 2026-10-29): identical executions, with the register a full import writes. On w2c,
    `verify --level chain` passed and `recompute --dry-run --jobs 12` (run alone) gave 67,711 identical, 0 unexplained,
    0 corpus-file differences; its tier-4 round trips were served from the validation cache (D-550), so that recompute
    did not re-run tier 4 under the CPU budget. The 210-call execution is in the corpus and derivable from its AER, but
    whether its prov job completes depends on the 300 s per-job CPU budget and the machine's load: it failed under the
    16-worker import and passed on the quiet machine (datasheet item 24). A per-source CPU
    budget for prov and validate jobs (`[import] prov_cpu_s`) would remove that dependence; it is left for v0.2.
  - **Rejected.**
    - Raising the default prov/validate caps for every source (it lowers the watchdog's protection for every import).
    - Raising the raw-input JSON limit (it would relax untrusted input to admit engine output).
    - Compressing context membership now (a class-2 change of PROV semantics for every corpus).
