- **D-54 (2026-10-12, phase 12b: no git call of the fetch layer may fetch lazily; absent blobs are a typed refusal;
  routing R2).** `GIT_NO_LAZY_FETCH=1` is part of the Fetcher's fixed git environment, so it applies to every call (the
  depth-1 store, the history store, the seeding tool's file-protocol fetch). `parse_ls_tree` refuses a tree in which any
  entry's size is `BAD` with `AbsentBlobError` (`raw.fetch.blob_absent`, carrying the absent paths as labels), and any
  other non-decimal size with `raw.fetch.git`; before, `int("BAD")` raised `ValueError`. `tools/seed_git_cache.py`
  prints the code (with a hint when the clone's config names a promisor remote) and exits with its status.
  - **Why / what was measured:** git ≥ 2.45.1 already disables lazy fetching inside `upload-pack` by default, so the
    routed case (seeding from a `blob:none` clone over the file protocol) failed without network use on git 2.54.0; but
    `GIT_NO_LAZY_FETCH=0` turns it back on, and **local reads** were not covered: `ls-tree -l` on a depth-1 store with a
    promisor remote fetched every absent blob from that remote (reproduced offline with a local upstream;
    `tests/unit/raw/test_fetch.py::test_without_the_guard_reading_a_partial_store_fetches_from_its_upstream`).
  - **Rejected:** refusing every partial clone up front (the phase-10d trial seeds from partial clones whose absent
    blobs lie outside the pinned paths); skipping absent entries (a half-read tree would pass expectations silently).
  - **Effect:** no AER, SEM or PROV byte changes; `fetch.py` is not an `expand` module.
