- **D-1001 (2026-10-30, `recompute` rebuilds a sealed corpus's ingest-limit overrides from the recorded source profile,
  accepted only when their digest equals the `aer` stage's recorded `limits_sha256`; approved by the user ("Yes to
  both", in the orchestrator's window) after the wave-2 pre-release checks found it; push pending; byte class 0).**
  D-358 after the wave-2 seal refused `mcphunt-w2b` with `corpus.derive.limits_mismatch`, at its building commit
  `f8b5d62b` and at `c0e711f4` (`docs/reports/release/wave-2-pre-release-checks.md`, check 7). `mcphunt@3` raises
  `max_json_element_bytes` to 64 MiB (D-288, D-323). A working `corpus.json` records the raise under `limits.overrides`,
  but the sealed manifest (`corpus-0.2`, a closed schema) has no `limits` record, so `recompute` replayed the defaults,
  and the importer's D-323 check correctly refused them under the same profile version. The import itself is
  consistent: the limits rebuilt from the profile hash to the recorded `sha256:f4058f07…a2a3`. Only `recompute`'s
  reading of a sealed manifest was missing. A sealed tree of any source whose profile raises a limit would be refused
  the same way.
  - **Decision.** `Derivation.recorded_limit_overrides` keeps `corpus.json`'s `limits` record whenever there is one.
    Without one, it applies the `[import] limits` of the profile that every `aer` stage records (one `id@version` and
    one `limits_sha256` for all of them) to the defaults. It returns their overrides only when
    `sha256(JCS(limits))` equals the recorded `limits_sha256`, and it then adds a notice. In every other case it
    returns no overrides, and the importer's `corpus.derive.limits_mismatch` refusal stands as before: no digest, two
    `aer` stages that disagree, a profile version the package does not ship, or a profile that declares nothing. The
    profile's declaration reaches `corpus/` through a new injected lookup, `Catalogues.profile_limits` (`cli/derive.py`,
    M.5.2(1)), as `worker_caps` does (D-935).
  - **Why the digest.** The recorded `limits_sha256` is the bound fact about what the import ran with. A match proves
    that the rebuilt limits are those limits. The rebuild never picks a value the record does not confirm, so D-323's
    rule against a silent pick holds.
  - **Bytes (class 0).** `corpus/derive.py` and `cli/derive.py` are in no stage scope: all 41 stage digests are identical
    before and after (`tools/r1/stage_digests.py`). Output bytes are unchanged for every corpus that recompute already
    accepted: a working corpus keeps its record, and a sealed corpus with no raised limit rebuilds nothing. Tests:
    `tests/unit/corpus/test_recorded_limits.py` covers:
    - the match case;
    - six mismatch and absent cases;
    - the importer accepting the rebuilt `mcphunt@3` limits and still refusing a mismatch;
    - the CLI lookup.
  - **Rejected.**
    - Option (a) alone, recording `mcphunt`'s D-358 as the pre-seal recompute plus the sealed chain: possible, but the
      fix is narrow, and the same refusal would meet every sealed corpus whose profile raises a limit.
    - Adding a `limits` record to the sealed manifest: `corpus-0.2` is closed and the 43 trees are sealed; a new
      corpus format is class 0 but changes every sealed manifest's bytes.
    - Reading the overrides from the current profile without the digest check: a silent pick, which D-323 forbids.
