- **D-704 (2026-10-22, `agentprov jobs` and `agentprov batch`; part of D-700; user decisions 2026-10-22: the job
  manager moves into the core with `$AGENTPROV_HOME/jobs` and no migration, psutil becomes a core dependency, and a
  batch runs as a job).**
  - **What (jobs).**
    - `agentprov.jobs`: `record` and `follow` are read-only, and the GUI imports them (D-391 allowlist). `tiers`
      holds the R0/R1/R2 and destructive rules, moved from the GUI. `manager` and `supervisor` are the write side,
      reached only through the CLI.
    - A job runs `agentprov ARGV` in this interpreter (`-I`), or one `tools/<name>.py` of this checkout, under a
      detached supervisor (`python -I -m agentprov.jobs.supervisor DIR`, a new session). The supervisor records both
      processes' `(pid, create_time)` in `job.json`, passes a SIGTERM on, waits, and writes `ended.json` with the
      real exit code. The detached `jobs start` cannot wait, as the GUI did.
    - `--tool` must name a regular file inside the checkout's `tools/`: relative, no `..`, no drive, no symlink
      anywhere on the way, and resolved inside `tools/`. Nothing else can be started.
    - The rules at start are the GUI's (§4.4): one writer per corpus, either a running job or an `.agentprov.lock`;
      one job per slot (`network`, `backends`); and a job never starts jobs or batches (exit 4).
    - `stop` sends one SIGTERM to the CLI after the identity check (POSIX). `kill --yes` takes the supervisor's
      whole tree by process group after the identity check, waits up to 5 s, and records `how: killed`. `drain`
      writes the D-394 control file (`--with-control-file`), `resume` starts the recorded request again, and `prune`
      lists old ended jobs and deletes them only with `--yes`.
    - The child environment is the GUI's allowlist plus `AGENTPROV_NO_KEYCHAIN`. `job.json` records variable
      names only.
  - **What (batches; user decision: a batch runs as a job).**
    - `agentprov.jobs.batch` keeps `$AGENTPROV_HOME/batches/<id>.json` (`agentprov-batch/0.1`).
    - `batch create SPEC` (or `--stdin`) checks every step with the CLI's own parser. It refuses a step that starts jobs or
      batches, a destructive one (`purge` without `--dry-run`) and malformed fields (exit 2), and records the checkout
      pin (path, commit, digest of `git diff HEAD`; GR-70).
    - `batch start ID` launches one driver job, `agentprov batch run ID`, with a job id chosen beforehand and
      recorded in the batch under its lock. The driver ticks every 2 s (lock, load, advance, save) until every step
      has ended. On SIGTERM it stops (exit 130), and the steps it started keep running.
    - Each step is checked again before it starts, because the file is not trusted (GR-4): the parse, no recursion,
      not destructive, and no tier above the one recorded. A failure blocks the step with a fixed note.
    - R2 steps run only when the batch's `r2_confirmed_by` names this driver, meaning it was started or resumed with
      `--confirm-r2`. `start` without it refuses (exit 4). A later driver without it holds at the first R2 step and
      ends (GR-48).
    - A changed pin blocks every remaining step. Exit 4 or 70 blocks the rest unless `--continue-on-failure`. The
      dev-run fallback (D-529: a first-N import after `import.sample.unsupported`, or the part's later steps
      skipped) moves along.
    - **This replaces** the GUI design's "the queue advances only while the GUI is open" (research §Q2): no
      always-on service, one driver job per running batch, visible in Runs and stoppable like any job.
  - **GUI (part 3).**
    - The GUI's `JobManager` keeps its names but is a client. `spawn` runs `jobs start --format json` with the spec's
      corpora, slot, queue CPUs, progress level, `--tool`, notes and `--meta` facts (backend, call cap, dev-run part).
      Refusals come back with the CLI's code (`jobs.writer.busy` …), and a CLI that cannot run gives
      `gui.spawn.failed`.
    - `refresh` reads the job files through `agentprov.jobs.record`, and the `--meta` facts are merged into
      `record`. `stop`, `kill`, `request` (drain) and the prune listing are `jobs` calls.
    - The GUI refuses `--env-stdin` and `--env-file` in any job, because it holds no keys (D-702).
    - Batches are read from `$AGENTPROV_HOME/batches` and created, started, resumed and stopped through
      `agentprov batch`. There is no advance timer, and the GUI's batch rules and the dev-run fallback helpers are
      gone; the core applies them.
    - The GUI tests' fake CLI hands `jobs` and `batch` to the core's own CLI, with the job program replaced in that
      test process only. The real CLI has no option or variable that runs another program.
  - **psutil** is a core dependency (7.2.2, locked offline from the GUI's lock). Only `jobs/` may import it, and a
    boundary test proves the allowance admits psutil alone. psutil imports `socket` for constants (as D-545 for the
    GUI); no `jobs` module opens a socket. M.5.1 puts `jobs` at L1, M.5.3 gains the psutil row and the subprocess
    importers, and the reviewed subprocess list (SEC-11) gains `jobs/manager.py` and `jobs/supervisor.py`.
  - **Rejected:**
    - keeping the job manager in the GUI (the CLI could not start or control jobs);
    - a stdlib-only process identity (`ps`, `/proc` and ctypes per platform; user decision);
    - the GUI's `waitpid` (the starter exits, so it cannot wait);
    - `--tool` with any path (arbitrary command execution).
  - **Class 0.** `jobs/` and `cli/` are outside every stage closure: `regen_pins --affected` against 4d6a8d57
    names no family.
  - **Tests:** `tests/jobs/test_jobs.py` (supervised exit codes, the allowlisted environment, stop and kill, the
    writer, slot and lock rules, drain, resume, prune, no recursion, the `--tool` attacks: `..`, absolute paths,
    drives, symlinked files, directories and `tools/` itself; tiers); `tests/cli/test_jobs_cmd.py`;
    `tests/jobs/test_batch.py` (unknown, recursive and destructive steps, a step whose argv now needs R2, a tampered
    batch file, R2 confirmation, the pin, blocking exits, one driver job); `tests/boundary` (the psutil-only
    allowance); `tests/security/test_static_dangerous_calls.py`.
  - **Amendment (2026-10-22, F-14 from the user-guide session): relative paths mean the caller's cwd.** A job runs in
    its own folder, so `agentprov jobs start -- validate --corpus corpora/x` used to end with `corpus.missing`.
    `jobs start` and `batch create` now make every relative path option of the subcommand absolute against the
    caller's working directory before the spawn, and record it that way (`subcommand_argv`, `writes`, `reads`). Path
    options are those whose metavar names a path (`PATH`, `DIR`, `FILE`, `*.toml`, `*.json`, `ROLE=PATH`…), as
    `--opt VALUE` or `--opt=VALUE`; `-` and URLs are kept. Positionals are rewritten from the parser's metadata too
    (follow-up, same day): a path metavar always (`validate FILE…`), `inspect TARGET` only when it is a path (it
    exists under the cwd, has a separator, or starts with `.` or `~`), never an execution id. A `--tool`'s own
    arguments are not rewritten. Chosen over refusing them: a shell user's relative path then does
    what they mean, and the record is still unambiguous. The GUI already passes absolute paths, so nothing it starts
    changes. Tests: `tests/cli/test_jobs_cmd.py`, `tests/jobs/test_batch.py`.
