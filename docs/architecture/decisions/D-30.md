- **D-30 (2026-10-11, `derive` and `recompute` live in `corpus/`, reuse the T1 job kind `prov`, re-map through
  `import_source` and always write a new corpus; phase 11, implementation ruling).** The engine is
  `agentprov.corpus.derive` (L5) with `corpus/rawtree.py` and the CLI module `cli/derive.py`. It never imports
  `adapters.runner` or `adapters.registry`; what it needs from the adapter layer (`Catalogues.source_profile_sha256`,
  `Catalogues.semantics`) is injected by the CLI (M.5.2(1)).
  - **Never in place.** Both commands read `--corpus SRC` (sealed, working or `.partial`) through `CorpusReader` and write
    `NEW.partial` (`--out NEW`). `NEW` must not exist, must be disjoint from `SRC` and from every sealed corpus, and
    outside git. `--dry-run` builds into a private temporary tree that is removed afterwards, so it derives and compares
    exactly what `--out` would. Tests wrap every command in `testing.fs_guard.unchanged(SRC)`.
  - **Re-map and re-derive.** A re-map (`expand` or `aer` requested) feeds `StoredRawTree` (one candidate per non-member
    origin row, read from the source store with a digest check, the recorded origin, no network) to the public
    `adapters.runner.importer.import_source(..., until="aer")` with the values recorded in the source manifest and
    `derivation.json`. A re-derive copies the stored AER after re-verifying its seal. In both cases SEM, PROV and tiers
    3-4 then run as the existing job kind `prov` (by name, in batches over `WorkerPool`, consumed in index order); no job
    kind was added to `io/workers.py`.
  - **Pinned duplicates.** The `sem`/`prov`/`validation` stage definitions, `code_sha256` and the importer's `finish()`
    logic are re-implemented in `corpus/derive.py` (the B2 completeness rule is `corpus.facets.completeness_of`);
    `tests/unit/corpus/test_derive_definitions.py` pins them equal to the importer's.
  - **Comparison (H.8.4).** Per execution, by bytes and digests only (AER bytes and execution digest, SEM digest per
    profile, PROV file sha256 per spec, validation-row JCS digest, view bytes). A changed output is `changed_explained`
    when the declared identity of its stage or of a stage upstream differs between the two `derivation.json` files (the
    stage definition minus `fn_digest`, `engine_code_sha256`, `adapter_code_sha256` and the digests that sit beside an
    integer version, D-31); otherwise `unexplained_change` (exit 1). `failed`, `unverified`, a code-digest-only change
    that passes with a notice, `index_refreshed` and the corpus-level files (register, origins, members; HL-T14) are
    reported separately. `--show-diff N` prints the first differing line and the PROV semantic diff (`prov/diff.py`).
  - **Inputs first, resume.** Every listed raw object is re-hashed (`raw.digest.mismatch`) and the recorded
    catalogue/profile digests are compared with the package (`rules.mismatch`, `rules.unavailable`) before `NEW.partial`
    exists. The first file written is the working `corpus.json` with `derived_from` (`command`, `corpus_id`,
    `corpus_version|null`, `manifest_sha256`, `recomputed`, `root_digest|null`, `state`); a run with the same
    `derived_from` resumes, keyed on the sealed AER recorded in the index row (never on file existence); a different one
    is refused (exit 4).
  - **`derive` versus `recompute`.** `recompute` re-runs the requested stages (default: every stage the source has, from
    raw) and compares. `derive` adds missing layers (`sem,prov,validation`, `views`, `compat`) and carries present ones,
    refuses a requested present layer whose package definition has another declared identity (exit 4), and cannot
    re-map. `derive --trig DIR` writes TriG (E.5.4, `prov/serialise/trig.py`) with a `trig.sha256` listing.
  - **Reuse cache.** An execution's SEM, PROV and validation outputs are carried instead of recomputed when the reuse key
    is unchanged: same sealed AER, the same `fn_digest` of the three stage definitions, the same interpreter and core
    lockfile digest, the same digests for every catalogue and source profile the AER header declares, and every output
    present in the source row. The key is content-addressed only (no time, size or mtime). `--out` runs reuse by default,
    `--no-reuse` forces a full recompute and is the proof that a reusing run gave the same bytes (tested across `--jobs`
    1 and 4, re-derive and re-map); `recompute --dry-run` never reuses. The run is recorded in `derivation.json` as
    `reuse: {enabled, reused, recomputed, recomputed_executions}`. The key is coarse by design: a semantics-profile or
    catalogue change used by every execution recomputes every execution, because which executions a rule change affects
    cannot be known without recomputing them.
  - **Measured (derive-timings.md).** Zero unexplained differences on copies of the Mandate (396) and AgentHarm (1,056)
    p10 corpora; about 7-9 executions per second at 8-12 workers on a shared M2 Max; a re-map adds 10-25 % to a
    re-derive; tier-4 `pv.roundtrip` is 83-86 % of the cost (fixes proposed to the `validate/` owner, not applied).
  - **Why:** `corpus/` sits below `adapters.runner` (M.5.2); one pipeline (the job kind and `import_source` that import
    an execution also re-derive it) makes a recompute of an unchanged corpus byte-identical (Q.14) and lets an adapter fix
    be applied to an existing corpus without the network; never in place keeps every corpus immutable and a recompute
    transactional.
  - **Rejected:** `corpus.derive` importing `adapters.runner` or `adapters.profiles`; a new job kind `derive`; the
    baseline's in-place recompute; comparing parsed documents (`true`, `1`, `1.0`); counting a code-digest change as a
    version change (it would hide unintended output changes behind refactors); resuming on file existence (baseline R6);
    a finer per-rule reuse key (a wrong guess keeps stale provenance); reuse in `--dry-run`; a reuse key with
    timestamps or file sizes; threads or free-threaded Python for speed (worker processes are a security boundary).
