- **D-242 (2026-10-13: JSON documents above `max_json_bytes` by declared-array streaming; user-approved 2026-10-13).**
  `ingest/jsonstream.py` `open_json_stream(source, limits, *, arrays, profile)`: the caller declares the arrays to stream
  (JSON Pointers of member names, at most 16, none containing another); a byte-level scanner cuts them into element slices,
  and every slice and the envelope (streamed arrays replaced by `[]`) is parsed by `strict_json_loads` itself, so the
  strict rules are the same code. Two passes, fail closed. New limits `max_json_stream_bytes` (1 GiB), `max_json_element_bytes`
  (16 MiB), `max_json_elements` (1,000,000) and code `ingest.json.elements`. Accepts exactly what `strict_json_loads`
  accepts, with an equal value (property and fuzz tests). Spec G.3.3. Design §3.
  - **Why:** MCPHunt's per-model documents reach 110.9 MB; `strict_json_loads` would hold about 2.6 GB of objects.
  - **Rejected:** a per-profile raise of `max_json_bytes` (needs a larger memory cap for a parser of untrusted bytes, which
    D-55 refused); a third-party streaming parser (stdlib-only); `raw_decode` retried on a growing buffer (cannot tell
    truncated from malformed; loses byte offsets; quadratic worst case); re-encoding as JSONL at fetch (edits raw bytes;
    needs an origin kind); a full event parser in Python (re-implements the rules that must stay identical; slow).
  - **Effect:** none on any digest: `jsonstream.py` is not an expand module and no code digest hashes `ingest/`. Used by
    the future MCPHunt reader (adapter session); the reader must pass a seekable handle (`JobContext.open_input`).
