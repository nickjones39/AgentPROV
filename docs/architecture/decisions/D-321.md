- **D-321 (2026-10-13, follow-up (ii) of R-10k-1: rejected rows of multi-execution files; design approved by the deferrals
  session; H.6.1 R5 ruling: option A, chosen by the user in the orchestrator's session and confirmed in this one).**
  - **Hook.** A `multi_execution` reader may define `rejected`, yielding `Rejected(locator, code, detail)` for the rows
    its `parse` does not yield. It runs only in the T1 map job, also for a file with no execution, whose rows then
    replace the file-level entry.
  - **Validation.** The parent validates every row before registering any: an allowed code
    (`select.not_execution_artefact`, `select.out_of_scope`), an element key locator that is neither an execution's nor
    a duplicate, and the register's detail check. An invalid row makes the file one degenerate AER
    (`adapter.rejected_invalid`).
  - **Registration.** Valid rows are registered in canonical locator order with subject `{source_key}` and disposition
    `not_imported`, so each counts as a candidate (R1/R5). A resume registers none twice. A re-map re-derives them and a
    re-derive carries them.
  - **Multi-snapshot.** A corpus with several snapshots is refused at sealing and `verify`
    (`corpus.manifest.unattributed`) until origin-based attribution (option B) is built. D.2.9 note item 13;
    `docs/reports/r10k1/followups-design.md` §1.
  - **Downstream:** no AER, SEM or PROV byte of any corpus (no shipped reader defines `rejected`). The `aer` stage's
    `engine_code_sha256` moves again for imports made afterwards.
  - **Rejected:** option C, one file-level entry only (D-300 asked for the rows, and rows inside a file with executions
    would stay untraced); option D, a `#line=n` suffix in the path subject (ambiguous, and against H.6.2's path);
    registering rows unchecked from T1 (the reader saw untrusted bytes); a partial registration when one row is invalid.
