- **D-29 (2026-10-11, DTap quality problems: settled handling; user-approved, specified in §D.16).** These are the
  user's rulings, relayed by the phase-10b coordination on 2026-10-11. Only the secrets policy remains open
  (§D.16.13).
  1. **Synthetic trajectories (20, `synthetic: true`)** are never executions. The raw is stored, the file is registered
     `select.not_execution_artefact` (role `not_executions`), and it is counted in the disclosure. The judge of such a
     directory is registered the same way.
  2. **Harness failures (47 OpenClaw runs, judged anyway)** are imported as executions with run status `error`; the
     error is observed (class O). The recorded judgements are kept verbatim beside the seal issue
     `dtap.judgement_on_failed_run`. They are excluded from attack and utility rates by default and counted separately.
  3. **Empty trajectories (17)** are `outcome_only` executions (the ROPE precedent): no invented steps, seal issues
     `no_execution_observed` and `dtap.empty_trajectory`, recorded judgements kept.
  4. **LFS-pointer trajectories (2):** step 3 fetches the two LFS objects by their pinned oid, verifies the sha256
     against the pointer, and imports them normally (downloads approved for phase 10b). If an object is unavailable,
     the file is registered as unresolved and is not an execution.
  5. **Re-judged results (458 `audit_correction`):** both values are kept as recorded judgements (class O), each with
     its own date and source as recorded. The dataset's audit field marks the corrected one effective
     (`dtap.audit_correction_effective@1`, D, citing that field; `recomputed`, `revises` the original). Stats default
     to the corrected value and report both.
  6. **Re-runs (1,291 task directories, and the `_N` files) under one judge:** every attempt is its own execution. The
     judge is linked to an attempt only when its recorded snippets or metadata match exactly one attempt's logged
     content (`dtap.judge_attempt_by_content@1`, D, citing both files). Otherwise it attaches to the directory group,
     unresolved: those attempts have no per-run outcome, are excluded from per-run rates by default, and are
     disclosed.
  7. **`(1)` copies (8)** are byte-identical: one execution with two origins (SEC-19 precedent). Differing bytes
     would make a separate attempt under item 6.
  8. **The partial trajectory (1)** is imported with a truncation seal issue (`dtap.partial_trajectory`, plus
     `incomplete_run`), with no gap filling.
  9. **`direct_prompt` `task_success`** (a constant, not a result) is kept as recorded (`harness_default`), marked
     non-informative in SEM and the assessment, and excluded from utility rates.
  - **Spec-level additions** (consistent with the rulings; open question 2 in §D.16.17): a judge in a
    single-trajectory directory without a content match is linked at class I (`dtap.judge_dir_colocation@1`); a
    directory holding only a judge yields an `outcome_only` unit (D.2.8). The seal issues use the `dtap.` namespace
    (C.12.3 is closed), and the register codes reuse H.6.3's closed set, with `dtap.*` only in `detail`.
  - **Why:** nothing fabricated becomes an execution; every recorded value is kept, beside the issue that qualifies
    it; rates exclude what is not a run outcome without deleting it; and identity stays content-addressed.
  - **Rejected:** dropping harness failures or empty runs (selection bias, invariant 7); replacing the original
    judgement by the corrected one (destroys a recorded value); attaching one judge to every attempt (it asserts
    outcomes for attempts it may not have scored); importing synthetic trajectories with a flag (they are not
    executions of anything).
  - **10. Secrets (user decision, 2026-10-11): option A, include.** The user judges DTap's secret-like strings to be
    synthetic benchmark data; every execution is imported and deposited, nothing is withheld, and no per-execution
    flag is raised. Unchanged: raw bytes are never edited, `env_vars` never enter derived records (configuration field
    allowlist), values are never tested, and the datasheet carries one general statement that the corpus contains
    injection payloads and secret-like strings by design. The open questions of §D.16.17 (judge co-location class I,
    role `agent` verbatim, catalogue-declared `stats` exclusions, runner items R1–R3 with phase-12 consultation

    - **Rejected:** B (withholding up to about 2,600 executions, skewing the deposit's CRM attack set); D (redaction

  - **Addendum (2026-10-12, user decisions on the DTap sample-corpus check, questions c1-c4 of
    `docs/reports/analysis/dtap-sample-check.md` §9.2; the four fixes b1-b4 were approved the same day).**
    - **Q1. Shared `raw:` entities that two documents of one corpus describe differently: accepted and disclosed.** A
      content-addressed `raw:` entity carries attributes relative to the execution that cites it: `apv:originPath` (a
      judge file byte-identical across task directories) and `apv:artefactRole` (a re-run attempt that is one
      execution's `primary` and a sibling's `supporting` artefact). Merging the documents of a corpus gives
      multi-valued attributes. That is valid PROV, as for the cross-corpus `apv:originRevision` variants examination 2
      accepted. Fix b2 (auxiliary media types, D.16.14) removes the `apv:mediaType` variants. On the re-imported
      500-run sample 61 of 877 shared keys still vary (as before b2): 45 judge files only in `apv:originPath`, 16 attempts
      only in `apv:artefactRole`; none in `apv:mediaType` (before: 16 in `apv:artefactRole` and `apv:mediaType`). The
      count is unchanged because every media variant came with a role variant. Datasheet item 16.
      - **Rejected:** moving `apv:originPath`/`apv:artefactRole` off the `raw:` entity to an execution-scoped node (a
        `prov/` change that alters the PROV of every corpus).
    - **Q2. Runs without an agent turn stay `verified_complete`.** In the sample, 6 of 498 agent executions (4 OpenClaw
      `direct_prompt` runs that log only the user step, 2 harness failures) have `dtap.acc.counters` as their only
      evaluated check, and it balances: 0 calls, 0 results. B2's rule (at least one evaluated check in an
      `agent_execution`) holds. Every run with an agent turn is `unverifiable`, because its model calls are derived.
      Datasheet item 14.
      - **Rejected:** requiring a core accounting check for `verified_complete` (an importer change for every family,
        for 6 runs whose counters do reconcile).
    - **Q3. At the full import, the corpus manifest records the pinned origin, never local staging paths.** The sample
      driver (`tools/dtap/import_dtap.py`) reads the staging worktrees through `LocalTree`, so `corpus.json` holds
      `{kind: local, path: "<home>/.agentprov/staging/..."}` beside the `runs` and `tasks` pins. The step-4 import must
      name the pins as the snapshot and context origins: through `agentprov import --verify-against-pin` once
      `raw/fetch.py` accepts Hugging Face dataset URLs (phase 12b item 4), or through an equivalent driver change.
      This is an AGENTS.md step-4 prerequisite.
      - **Rejected:** keeping the `<home>`-masked paths (the manifest would not name what the corpus was built from).
    - **Q4. Byte-identical judge-only files from different directories: one execution with two origins.** Identity stays
      content-addressed (D-27 c2, SEC-19; item 7 above). In the sample, the judge files of two judge-only directories
      of different tasks (`openaisdk/gpt-5.1/telecom/malicious/direct/privacy_leak_address/007` and
      `.../indirect/credential_leak/001`) are byte-identical. They give one `outcome_only` execution with two origins,
      whose task facets name the first directory; the second directory is a `dedup.collapsed` register row. So
      judge-only outcome units count distinct judge files, not directories. Per-directory counts remain possible from
      the origins (`raw/origins.jsonl`, the register). Rates are unaffected: `dtap.rate.outcome_only` excludes these
      units. Datasheet item 15.
      - **Rejected:** making the path part of a judge-primary unit's identity (it breaks content addressing for one
        kind of unit, and it is a mapper change for a count that the origins already give).
