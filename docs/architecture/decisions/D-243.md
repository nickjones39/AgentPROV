- **D-243 (2026-10-13: zips stored as byte parts; user-approved 2026-10-13).** `ingest/parts.py` `PartsView` (read-only, seekable, the
  declared order) and `ingest/archives.py` `open_split_zip(parts, sizes, limits, *, release, depth)`: the declaration gate
  (`ingest.archive.parts`: 2..`max_split_parts` parts, none empty, each its declared size, logical size ≤ `max_split_bytes`),
  then G.3.5 unchanged on the logical bytes. `raw/members.py`: `ContainerSpec.parts`, a multi-input `expand` job (the
  descriptor, then the parts, each opened by digest), the worker refusing inputs that are not the descriptor's parts in
  order. New limits `max_split_parts` (64), `max_split_bytes` (8 GiB). Spec G.3.5. Design §4.
  - **Why:** control-arena's three logical zips are 8 + 8 + 3 parts of 256 MiB; two are within 9,191 B of
    `max_artefact_bytes`. Order never comes from names (`part-0000` sorts, but a name is a label, G.3.6).
  - **Rejected:** reassembling the zip in T0 or on disk (duplicates bytes; an extraction-like step); trusting part names
    for order; PKWARE multi-disk support (no source uses it; the pre-check keeps refusing it).
