- **D-620 (2026-10-22, ultrareview pre-round fixes, seal-release findings #2, #8 and #9; user-requested 2026-10-22,
  relayed by the orchestrator: "fix every finding"; branch `integration-fix-ultra-b`). The release gates anchor on
  what is published outside the deposit and on the pinned scanners.**
  - **1. A deposit needs a published root digest in release mode (#8, `3230e25e`; amends D-39 item 3).**
    - **Problem.** `release/verify.py` refused a missing `--root-digest` in release mode only for a lone meta
      archive. For a deposit directory it passed `deposit_manifest=True`, which skips the D-39 requirement, because
      D-39 held that `DEPOSIT-MANIFEST.json` anchors the root digest. It does not: it lies in the same untrusted
      directory as the archives. A deposit forged end to end (archives, the checksums inside them, the deposit
      manifest) passed `verify --release` with exit 0.
    - **Rule.** `verify --release` on a deposit directory needs at least one `--root-digest`, as tree mode and a lone
      meta archive do: the same `VerifyUsageError` (exit 2), raised before the interpreter guard and before anything
      is read. Each given digest must still match one corpus of the deposit (`root_digest.mismatch`). Without
      `--release` the option stays optional everywhere.
    - **Rejected:**
      - Reporting the root digest as `unverified` instead of refusing. Release mode fails every `unverified` finding
        anyway, and a usage error names what is missing before any work is done.
      - Keeping the deposit manifest as an anchor. That is circular, as D-39's own rejected alternative says.
      - Requiring a digest for every corpus of a multi-corpus deposit. It was not requested, and D-39 item 2's
        per-corpus rule is unchanged (see Open).
  - **2. The datasheet copy of a mixed-licence-class deposit is compared in full (#9, `71979682`; amends D-490 rule
    3).**
    - **Problem.** With mixed licence classes the D-490 check tested only that `DATASHEET-<id>.md` starts with the
      archived `DATASHEET.md`, a newline and the note header. Text after the header (a different licence statement,
      extra claims, injected text) passed, even with `--release` and the published root digests, once the deposit
      manifest's sha256 and md5 were updated.
    - **Rule.** The builder's copy is deterministic, so `verify` rebuilds it and compares bytes.
      1. `class_text` and `datasheet_copy` are pure functions in `release/metadata.py`, moved unchanged from the
         builder, which now calls them. Builder and verifier share one definition.
      2. The inputs are anchored: the archived `DATASHEET.md` and the licence class of each archived `corpus.json`
         (`licence_class`, as the builder computes it). The deposit's classes are recomputed from those manifests,
         not read from the deposit manifest.
      3. The deposit manifest's `mixed_licence_classes` must agree with them (`deposit.manifest.invalid`).
      4. A class that cannot be read, or a corpus entry that was not read, leaves the copies unverifiable:
         `deposit.document.datasheet` (failed; fail closed).
    - **Rejected:**
      - A longer prefix or a pattern match on the note: free text would still pass.
      - Trusting the deposit manifest's `licence_classes`: they are not anchored.
      - A second copy of the note text in the verifier: it could drift from the builder.
  - **3. The release-scan gate enforces the pinned scanners (seal-release #2, `77c07e77`).**
    - **Problem.** `check_release_scan` only checked that the scan document named a tool `gitleaks` with some
      version, and `tools/release_scan.py` recorded whatever gitleaks was on `PATH`. A scan from another gitleaks
      (other default rules), another configuration, or an older `release_scan.py` (path scan below 4: no D-457
      account-path or D-600 secret-shape search) was accepted as the G.9.4 scan.
    - **Rule.** The pins live once, in `agentprov.release.metadata`:
      - `GITLEAKS_VERSION` (8.30.1), and `GITLEAKS_CONFIG` with its `GITLEAKS_CONFIG_SHA256`;
      - `PATH_SCAN_TOOL` (`agentprov-path-scan`) and `PATH_SCAN_VERSION` ("4").

      The tool imports them. The deposit builder refuses with `release.refused.scan_tools` (exit 4) unless the
      document lists, each exactly once, gitleaks 8.30.1 with that `config_sha256` and the path scan at version 4.
      Recorded values are never echoed. The tool exits 3 (`ScanError`) for an unpinned gitleaks, before it scans or
      writes anything.
    - **Rejected:**
      - A minimum version instead of an exact pin: default rules change between gitleaks releases.
      - Keeping the pins in the tool only: the builder could not check them without importing `tools/`.
  - **Downstream effects.**
    - **Byte class 0 for all three.** `release/`, `corpus/verify.py`, `cli/` and `tools/` are in no stage digest
      (`stage_scopes.py`) and in no `EXPAND_MODULES` file. No AER, SEM, PROV, manifest, datasheet or deposit byte
      changes. Builder output is byte-identical: a probe over 160 synthetic inputs hashed the same before and after
      the move, and `tests/unit/release` passes.
    - **Users.**
      - `agentprov verify --release --corpus <deposit>` now needs `--root-digest` (exit 2 otherwise).
      - A mixed-class deposit with edited note text now fails, as does one whose `mixed_licence_classes` disagrees

      - A `<corpus>.release-scan.json` written by an older tool, another gitleaks or another configuration is
        refused. **Re-run the scan** with the current `tools/release_scan.py` and gitleaks 8.30.1 before building a
        deposit.
    - **Spec:** HL H.5.5 and H.10.3 items 1 and 2, MN N.2.6, G.9.4, the D-39 report, and D-39 and D-490 above.
    - **Tests:**
