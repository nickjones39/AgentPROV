- **D-790 (2026-10-23, the Zenodo draft-upload helper is built as `tools/zenodo_draft.py`; the user decided to build it,
  addendum to D-5; Addendum B B-2 is unchanged).** D-5 required an upload script that creates an unpublished draft of a
  new deposition from the user's own `ZENODO_TOKEN`; nothing was built, and H.10.1(2) and G.9.1 said "a future helper" and
  "AgentPROV never uploads". The helper now exists and those texts describe it exactly.
  - **What it is:** `tools/zenodo_draft.py`, standard library for the network (`http.client`, `ssl`), outside
    `agentprov.release` and outside the installed package, so H.10.1(1) holds unchanged (its static test passes). Input
    is a deposit draft made by `package --deposit`. `--target sandbox|production` is required with no default; the hosts
    are the fixed list `sandbox.zenodo.org` and `zenodo.org`, HTTPS with certificate verification, no redirects, no
    environment proxy. Plain HTTP exists only for `127.0.0.1` through a `run()` parameter no option reaches.
    - **Before any network access:** the directory is closed-world (the manifest's archives and documents plus
      `DEPOSIT-MANIFEST.json`, regular files only); every file's size, sha256 and md5 equal the manifest's; archive-mode
      `verify` (chain, release mode) passes; the file count and sizes are within the named constants `MAX_FILES` (100),
      `MAX_TOTAL_BYTES` and `MAX_FILE_BYTES` (50 GB, taken as 10^9, the smaller reading); `deposit-metadata.json` maps
      onto Zenodo's metadata. A deposit with more than one licence class or an SPDX id with no mapped Zenodo id is refused.
    - **Consent:** `--create-draft` (or the offline `--check`), a terminal on stdin and stdout, and a typed phrase naming
      the host after a screen that shows the host, every file with its bytes and sha256, the title, version, licence and
      creators, and "this creates an unpublished draft; nothing is published". There is no `--yes`.
    - **Requests:** an allowlist of method and path, checked before a socket opens: create a deposition, `PUT` its
      metadata, `GET` it and its files, `PUT` each file to its bucket (the link taken from the server only when it points
      at the target host), and `POST .../actions/newversion` only when the deposit metadata records a `concept_doi`, the
      deposition's concept DOI equals it, and neither is the AgentDojo-PROV concept (`10.5281/zenodo.20692312`). No
      publish, edit, discard or delete request exists in the code or the allowlist.
    - **Integrity:** the md5 and size Zenodo returns for each upload must equal the manifest's, and the draft's file list
      is read back and compared at the end; a mismatch stops the run, is reported and deletes nothing.
    - **Receipt:** `<deposit dir name>.zenodo-<target>-draft-receipt.json` beside the directory (never inside, because
      the directory is checksummed; the target is in the name so a sandbox trial does not block production). It is
      written before the first request, so a second create is refused and an interrupted create cannot silently repeat; a
      clear rejection (HTTP below 500) removes the pending receipt. `--resume` uploads only the missing files to the
      recorded, still unpublished draft after re-checking the directory against the receipt.
    - **Token:** read from `ZENODO_TOKEN` or `ZENODO_SANDBOX_TOKEN`, held in an object whose `repr` and `str` hide it,
      sent only in the `Authorization` header, removed from every printed line (error text before it is cut), never in a
      URL or the receipt; no traceback is printed.
  - **Known limits, for the user to confirm in the sandbox trial:**
    - the limits and the SPDX-to-Zenodo licence ids are from the public REST API documentation (read 2026-10-23, the user's
      yes) and are unconfirmed against the live service;
    - `newversion` makes a draft that inherits the previous version's files, and the helper never deletes, so it reports
      them (exit 1, receipt status `inherited_files`) for the user to remove in the web UI before Publish;
    - related identifiers with no Zenodo relation (`HasVersion`, ...) are listed on the consent screen as not sent.
  - **Rejected:**
    - upload code inside `agentprov.release` (breaks H.10.1(1) and the offline guarantee its test enforces);
    - an `agentprov` subcommand (puts a network client, a token and a publish-adjacent API in the installed package and
      its `--help`, and the GUI's CLI parity would offer it as a button, where consent must be a person at a terminal);
    - the third-party clients (`zenodo_client`, `invenio` tools, `requests`: a dependency in the path of a secret, with
      redirects and proxies followed by default);
    - a `--yes` flag or a non-interactive mode (consent must be a person at a terminal);
    - environment overrides for the host (a way to send the token elsewhere).
  - **Byte class 0:** a new file under `tools/`, tests, spec text; no file of any stage scope changes.
