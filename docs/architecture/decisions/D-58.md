- **D-58 (2026-10-12, phase 12b: streaming `expand`; HL.R7, D-47 item 3).** `JobContext.open_input(index)` opens a
  store object with the no-follow opener, hashes it in 1 MiB chunks, checks the digest, rewinds and returns the handle
  (`read_input` is built on it). `job_expand` passes that handle to `open_archive`; the nested-`tar.gz` path reads it in
  chunks too (`iter_gzip_bounded` takes a handle). Members are still read whole before their header is sent (a defect
  never yields partial bytes), bounded by `max_member_bytes`. Evidence: `docs/reports/hardening/expand-calibration.md`
  (peak 505 → 134 MiB on a 380 MB archive, CPU unchanged).
  - **Residual:** the bytes are hashed, then read again through the same descriptor. A store object is 0444 and the
    worker cannot write files (`RLIMIT_FSIZE = 0`), so only a writer outside the worker could change it in between.
  - **Rejected:** streaming member bytes into `DATA` frames before the CRC check (a defect would leave a half-sent
    member); `mmap` (the same check-then-use gap, and a platform difference).
  - **Effect:** `raw/members.py` and `ingest/` are `EXPAND_MODULES` (expand bundle); member digests and rows are
    unchanged (the level-2 and SEC-07 tests compare them across worker counts).
