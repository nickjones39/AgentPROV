  `update install` printed an upgrade command. The app runs its CLI through `CliLocator` (the checkout's `.venv`, else

  - **Decision: the bundle is its own `agentprov`.** The bundle's one executable answers, before Qt is imported
    (`gui/packaging/entry.py` → `agentprov.cli.frozen.dispatch`): `AgentPROV --cli ARGS` (= `agentprov ARGS`), the
    argv the core itself starts with `sys.executable` (`-I [-B] -m MODULE` for exactly `agentprov`,
    `agentprov.jobs.supervisor`, `agentprov.worker`, `agentprov.keys.helper` and `agentprov.update.apply`; a test
    scans the core for `-m agentprov…` argv and fails on a module the bundle does not answer), and `--keychain-helper`.
    Any other module, a script path or `-c` is refused (exit 2): the bundle is not a general interpreter, so
    `agentprov.host`'s `RLIMIT_AS` probe (`-c`) is "not decided" there and the worker pool falls back as on a host
    where the probe cannot run. `multiprocessing.freeze_support()` runs first (the priors builder's pool). The spec
    collects every core module, `agentprov_capture`, keyring's backends and rdflib's plugins; not the `render`,
    `shacl` and `live` extras or `agentprov-zenodo`. `CliLocator` falls back to it when no checkout is set and no
    installed `agentprov` is found, and Settings › General's new **agentprov to run** (`paths/cli_choice`:
    Automatic, or The app's own) can choose it always; it is then updated with the app. `update install` run by it
    reports the kind `bundle`. **What still needs a checkout:** live runs (`run`, `backends`, `migrate` find
    `backends/` from a checkout; Run Live now says so before a start when the CLI is the app's own), the job queue
    (`--queue-cpu`, `tools/suite_queue.py`), the checkout's tools (`jobs start --tool`), the Zenodo uploader, and
    `render` (Graphviz and the extra). When the bundle's own CLI swaps the bundle it runs from, everything used after
    the swap is imported before it (a module first imported afterwards would come from the new bundle's files), and on
    Windows the helper runs from a copy of the new bundle in `.AgentPROV-update-helper/` beside the app, since a
    helper running from the folder it renames could never rename it (a leftover copy with its marker is removed at the
    next install; a folder without it is refused). The bundle build's smoke step checks `--cli --version`, `-I -m
    agentprov --version` (the bundled core's version) and that `--cli update install` names the kind `bundle`. On
    Windows the bundle is a GUI-subsystem executable, so for `--cli` started from a console it attaches to the parent
    console and reopens only the streams Python has none of (`AttachConsole(ATTACH_PARENT_PROCESS)`, `CONOUT$`,
    `CONIN$`); a pipe from the app or a job is kept. The Windows paths are untested by the project's tests and the
    release notes say so.
  - **Decision: a package install from the release's own wheels.** `agentprov update download --package
    --allow-network` (R2) stages in `$AGENTPROV_HOME/update/staging/package/` (or `--dir`), in this order:
    `SHA256SUMS` and `SHA256SUMS.sig`, verified by D-1065's rule (a listed key requires a valid signature); then the
    release's `agentprov_capture-X-py3-none-any.whl`, `agentprov-X-…whl` and, when installed here,
    `agentprov_zenodo-X-…whl`, each with the listed size (at most 64 MiB) and sha256; then each wheel read, never
    unpacked: at most 10,000 members, no absolute, `..`, backslash or drive name, no encrypted member, and one
    `<dist>-X.dist-info/METADATA` naming that distribution and version. A failure removes what was fetched. Its
    document (`agentprov-update-download/0.1`, `kind: package`) also says what installing would do: `install_kind`,
    `from_version`, `to_version`, `parts`, `installer`, `installer_argv`, `installable`, `problems`,
    `keeps_previous: false`, `restore_command`. `agentprov update install --package --confirm` (R2; exit 4 without
    `--confirm`) verifies every staged file again (a changed wheel or list is refused), refuses a downgrade (exit 4),
    reports the same version as current, and runs the program's own installer on exactly those files with no
    resolver and no index: `pip` → `<its interpreter> -m pip install --no-deps --no-index --disable-pip-version-check
    --no-input WHEELS` (a venv without pip: `uv pip install --python <it> --no-deps --no-index`); `uv-tool` → `uv pip
    install --python <its interpreter> --no-deps --no-index WHEELS`; `pipx` → `pipx runpip <venv> install --no-deps
    --no-index …`; the installer's environment drops `PIP_*`, `UV_*`, `PYTHON*`, `VIRTUAL_ENV`, `CONDA_*`. Because
    nothing is resolved, it refuses (exit 4, `update.package.dependencies`, with the ordinary upgrade command) a
    release whose wheels need anything the installed version did not declare: every non-sibling requirement must
    equal, after normalising, one the installed distribution already has (so it is already satisfied), and every
    sibling requirement must be `==X`. Afterwards the installed versions are read again and must be the release's
    (`update.package.installed`). The install is recorded in `$AGENTPROV_HOME/update/package-installed.json`. **The
    previous version is not kept** (a package manager installs over it, and the old wheels are not on the machine):
    the output says so and names the command that goes back (`uv tool install --force agentprov==OLD`, `pipx install
    --force agentprov==OLD`, `<python> -m pip install agentprov==OLD agentprov-capture==OLD`, from PyPI).
  - **Decision: the checkout is updated in the same flow.** The user asked that the update also pull the checkout, so
    when the app runs from a checkout, the one confirmation lists the checkout as a part (commit from → origin/main's
    newest) and the flow updates it with no second prompt; in a terminal it is `agentprov update install --checkout
    --confirm --allow-network` (R2; the network flag for the fetch). It updates the editable install's own checkout
    (from its `direct_url.json`; the folder must be an AgentPROV checkout) only when the branch is `main`, its upstream
    is `origin/main`, `origin` is one of the project's GitHub repositories (`nickjones39/AgentPROV`,
    `nickjones39/agentprov-framework`, https or ssh), `git status --porcelain=v1 --untracked-files=normal` prints
    nothing, and `git rev-list --count origin/main..HEAD` is 0 (no commit origin lacks), checked against the last fetch
    and again after this one. The steps are `git pull --ff-only origin main` split so the ahead check sees the fetched
    state: `git -C ROOT fetch origin main`, the check, `git -C ROOT merge --ff-only FETCH_HEAD`, then `uv sync --frozen
    --group docs --project ROOT`, with every `GIT_*`, `UV_*` and `PYTHON*` variable dropped and
    `GIT_TERMINAL_PROMPT=0`. Nothing is ever discarded: no `reset`, no `stash`, no switch of branch (a test fails on
    any). When a condition fails, or the merge is not a fast-forward, the checkout step is skipped with the reason and
    the commands, and the other parts are still updated. A failed fetch or merge changes nothing and syncs nothing; a
    failed sync is reported with its command. The old commit is reported with `git -C ROOT reset --keep OLD` and the sync that go back.
    Otherwise nothing is touched and the reason is shown with the commands. Without a flag, `update install` keeps
    printing the upgrade command and adds `automatic` (`how`: `package`, `checkout` or `bundle`; `available`; `why`;
    for a checkout the facts read with local git only), which the app reads.
  - **Decision: the app, one confirmed flow.** About's **Download and Install…** (and Update Now) now covers both
    parts. When the program the app runs is behind and is not the app's own copy (`CliLocator.kind`), it first runs
    `update install --format json` (changes nothing) to learn the way; then `update download` for the app (when the
    app is a bundle and behind) and `update download --package` for a package install; then one confirmation names
    every part to be replaced (the app's folder or the program's install, versions from → to, how it was verified,
    what is kept: `.AgentPROV-previous`, nothing, or git's history) and every part that cannot be updated, with why
    and the command to run; only after Install it runs `update install --confirm --bundle`, then `update install
    --package --confirm` or `update install --checkout --confirm --allow-network`. A part that cannot be updated is
    never attempted; a failed part does not stop the next, and each reports itself. D-1070's notice wording follows:
    when only the program is behind, the notice and About offer **Update agentprov…** (replacing Show the Upgrade
    Command), which updates the program after the confirmation when it can and otherwise shows its command, and the
    app is not downloaded or replaced. GUI forward parity: `update download --package`, `update install --package`,
    `--checkout` and `--allow-network` are form fields; `--confirm` stays managed.
  - **Decision: the Terminal command (Install Command Line Tool…; the user's yes of 2026-11-06).**
    `agentprov launcher install|remove|status` (`agentprov.cli.launcher`, format `agentprov-launcher/0.1`; spec MN
    N.2.17 row) and the app's Install Command Line Tool… and Uninstall Command Line Tool (the AgentPROV menu on macOS,
    Help on Linux and Windows; shown only in a bundle; they always run the bundle's own CLI) write a launcher named
    `agentprov` (Windows: `agentprov.cmd`) in `~/.local/bin`, or a `--dir` that exists and is writable. The launcher
    runs `"EXE" --cli ARGS`, EXE being the bundle's executable by absolute path, so an app update updates it. It exits
    127 with a message when the app has moved or been deleted. Its second line is the marker `agentprov-launcher/1`:
    install replaces and remove deletes only a marked launcher. Any other `agentprov` (pip, uv tool, pipx, a `.venv`
    link; on Windows also `agentprov.exe`/`.bat`/`.com` in the folder) is refused with exit 4 and named. The reply
    gives the line that puts the folder on PATH and names an `agentprov` that comes first. The GUI's D-1030 lookup
    (`installed_program`) skips marked launchers, so the precedence (checkout, installed agentprov, the bundle's own)
    is unchanged and the app never runs itself through its launcher. On macOS, a real bundle built from the branch
    ran `AgentPROV --cli launcher install`; `agentprov` worked through PATH, a reinstall was unchanged, a moved app gave
    exit 127, and remove worked. Windows has not been tested. **Rejected:** a symbolic link to the bundle's executable
    (it would start without `--cli`, so the app opens, and it dangles silently when the app moves); a copy of the
    executable (an app update would not update it); `sudo` or elevation for `/usr/local/bin` (the app never asks for a
    password; that folder is offered only when it is already writable); editing shell profiles or the Windows user
    PATH (writes outside the app's scope; the reply gives the line instead); recognising the launcher by its path
    rather than a marker (pip's `agentprov` lives at the same `~/.local/bin` path). Tests:
    `tests/cli/test_launcher.py` and `gui/tests/test_cli_launcher.py`, with a temporary HOME, PATH and shared folder.
  - **Decision: nothing is replaced under a running job.** Jobs are detached processes that outlive the app and import
    modules lazily, so replacing the files they run from could break them part of the way through. `update install
    --confirm --bundle`, `rollback --yes`, `install --package --confirm` and `install --checkout --confirm` first list
    the running jobs of `$AGENTPROV_HOME/jobs` (`agentprov.jobs.record`, read only) whose recorded argv names a file
    inside the folder to be replaced (the bundle; the package's `sys.prefix`; the checkout, its `.venv` included),
    comparing paths as given and resolved, and refuse while any runs (exit 4, `update.install.busy`), naming them
    (escaped) and saying to stop them (Runs › Stop, `agentprov jobs stop ID`) or wait; nothing is stopped by the update
    (`agentprov.update.busy`). In the app the refused part says so and the other parts go on. The backend rebuild
    applies the same rule to an environment a running live job uses.
  - **Decision: stale backend environments are rebuilt after an update.** A checkout update can change a backend's
    lock or the T0 identity its environment was built from, and `run` then refuses that environment. The last step is
    `agentprov backends rebuild-stale [--allow-network]` (MN N.2.10; in the app it starts once the program part has
    installed, and the one confirmation names it, `UpdateController.followup`/`after_update`; Runs › **Rebuild Stale
    Environments…** runs it by hand). An environment is stale when the checks `run --catalogue` makes refuse it (no
    complete marker; the T0 identity against the marker and the lock; the NLTK zip; the Inspect dataset; the defence
    assets of `--offline-check`). Each stale one is built in turn as `backends build` does and then verified offline;
    only the environment the checkout names is written. A failure is recorded with its code, reason and command and
    does not stop the others (exit 3 if one failed); a backend the host cannot build (D-1064) is `unsupported`, not a
    failure; a stale backend a running live job uses is skipped as `busy`; one that holds defence assets is `blocked`
    with the command that rebuilds it with them (see the review below). Outside a checkout it refuses
    (`backend.repository_missing`). Report format `agentprov-backends-rebuild/0.1`. **Rejected:** (a) rebuilding every
    backend on every update (a full build of each backend whose environment is still accepted); (b) deleting or renaming the old environments
    (an environment is named by its backend and pinned upstream commit, so after a pin change the old one stays beside the new for an earlier checkout); (c) carrying `--defence-assets` over automatically (it may
    need a defence source or a download the user did not choose); (d) fetching the AgentHarm dataset automatically (its
    consent step is the user's); (e) rebuilding under a running live job (its environment would change part of the way
    through: it is skipped as busy instead). Its known limit: a change to `backends/shared` without a re-lock is not
    detected (rebuild that backend with `backends build`). Tests: `tests/cli/test_backends_rebuild_stale.py` (fake
    environments and builder) and the GUI's rebuild cases; a real offline rebuild of `agentdojo` in a temporary home
    passed `--offline-check`.
  - **Threat model.** Signature first (no wheel is fetched before the list verifies); no unverified byte installed
    (each installed file listed, sized and hashed, re-checked at install); no PyPI fetch (no resolver, no index, the
    index variables dropped, a dependency change refused); the user confirms each replacement; a dirty or foreign
    checkout is never touched. Spec G.7.8.
  - **Digest effect:** none. `update/`, `cli/`, the GUI and the packaging are outside every stage scope (checked
    against `stage_scopes`: of the code touched, only `host.py` and `io/workers.py` are in a closure, and neither is
    changed); no AER, SEM, PROV, validation or corpus byte moves.
  - **Documentation.** Every place that describes installing or updating says what the app download includes (its
    own `agentprov`), when a pip, uv tool or pipx install or a checkout is still needed, that live runs need a
    checkout, and how each part updates: user guide chapters 1, 7, 8, 10 and 11 (and the index), the repository
    README, the PyPI description, the website's download section and the v0.2.1 release notes.
  - **Rejected:** a forced checkout update (`git fetch` + `reset --hard origin/main`, or a stash around a dirty tree):
    it would delete unpushed commits or uncommitted work, and the user's request was to pull, not to discard;
    `uv tool install --force WHEELS` for a uv tool install (it resolves every dependency again, an index
    fetch, and rewrites the tool's receipt to a staging path that a later `uv tool upgrade` would follow);
    `pip install --upgrade agentprov==X` from PyPI (an unverified download, and what D-1065 already prints); trusting
    the wheels' own `RECORD` hashes (they come with the file they vouch for); installing the new dependencies too from
    the release (the release publishes only the project's wheels); keeping the old version by building a wheel from
    the installed files (`RECORD` lists them, but a rebuilt wheel is not the published one and could not be verified);
    running the GUI's own Python to install (the app has no network code, S11, and its interpreter is not the
    program's); `git pull` on any branch (another branch is the user's); a general `-c`/script interpreter in the bundle
    (the bundle would run any code handed to it); a separate CLI executable beside the app (a second PyInstaller
    target doubles the bundle and its signing); updating the program silently when the app updates (every
    replacement is confirmed, D-1065).

  - **Review and fixes before release (2026-11-06, the user's request "i want all issues fixed").** An independent
    review of the whole D-1130 range and of `backends rebuild-stale` (report in the session notes) found, and these
    fix:
    - *The bundle's own agentprov recorded false code digests.* `stage_definitions.code_sha256` (and the stage
      digests) hash the core's source files on disk, and the bundle held bytecode only and no metadata for `prov`
      (or `agentprov-capture`), so a corpus written by it would claim other code and `prov: absent`. The spec now ships
      the core's and the capture library's `.py` files (`collect_data_files(..., include_py_files=True)`) and the
      metadata of `agentprov.cli.frozen.RECORDED_DISTRIBUTIONS` (`copy_metadata`); `build_bundle.check_core_sources`
      fails the build unless the bundle's `agentprov` folder holds exactly the build environment's digested files and
      those distributions' metadata at its versions, and a smoke step runs a digest-recording command. As a backstop,
      `agentprov.cli.frozen.sources_problem` makes a bundle without them refuse every command outside
      `SAFE_WITHOUT_SOURCES` (exit 3). A real macOS bundle built from this branch passed both. **Rejected:** refusing
      corpus commands in every bundle (the app-only user loses import and derive, which D-1130 promised); recomputing
      digests from the PYZ bytecode (a bytecode digest is not the source digest a pip install records).
    - *Checkout:* `uv sync` is exact, so the sync names every installed extra again
      (`checkout.installed_extras`: the extras of `agentprov` whose requirements are installed); the step refuses when
      the program runs from another environment than `ROOT/.venv` (`UV_PROJECT_ENVIRONMENT` would leave it behind), and
      when a fetched commit adds a path that exists on disk (`git diff --name-only --diff-filter=A -z HEAD FETCH_HEAD`:
      git overwrites an ignored file without asking). **Rejected:** `--inexact` (it would also keep packages the new
      lock removed).
    - *Package:* `pip --isolated` / `uv pip --no-config` (no `pip.conf`/`uv.toml`); a user-site install gets
      `--user` (pip otherwise writes the base environment and the old copy stays first) and, without pip, is refused;
      the running-job guard covers the environment, the distributions' install folder, the `agentprov` commands the
      `RECORD` names and, for a uv tool, the `agentprov` on `PATH` (`package.install_folders`); the restore command
      takes `agentprov-zenodo` back too; a staged download lacking a distribution installed since is refused.
    - *Verification:* a missing or unreadable `allowed_signers` is refused (`update.verify.keys`, exit 3), never read
      as "no key listed".
    - *Windows helper:* a copy of the running bundle, never of the one a rollback restores (0.2.0's executable would
      open the app for `-m agentprov.update.apply`).
    - *Self-swap:* a test runs the bundle install in a fresh interpreter and fails on any module first imported after
      the swap; the GUI loads what runs after it before the first part (`UpdateController.prepare`,
      `jobs.rebuild.prepare`).
    - *Launcher:* refuses an app path that will not last (macOS App Translocation, a read-only disk image); on Windows
      the app's own folder is refused as the app's. *Console:* the attached streams are UTF-8 with `errors="replace"`.
      *Entry point:* `entry.py` imports `agentprov.cli.frozen` only for a CLI call (D-391).
    - *GUI flow:* each part's failure stays in the outcome and the status names every part not updated; a command
      that cannot run at all does not stop the chain (`after_update` still runs once); the confirmed installs run
      without a time limit (a kill could leave a package install half replaced); nothing is installed when the CLI the
      app runs changed between the plan and Install (`UpdateController.identity`; **rejected:** pinning the locator
      for the flow, which would install with a CLI the user had just replaced); the checkout part says "Source", not
      "Verified"; an unsynced checkout says so; `--gui-version` is this app's own; the launcher dialogs read the reply
      with the bounded strict reader and show its text escaped.
    - *rebuild-stale:* a stale environment that holds defence assets is `blocked` (`backend.defence_assets_kept`)
      with `backends build BACKEND --defence-assets IDS`, never rebuilt in place without them (**rejected:** carrying
      the assets over automatically, which may need a defence source or a download the user did not choose); a
      `run` job is matched by its source anywhere in the argv (the GUI puts positionals last) and a running `batch
      run` driver with a live step on the backend still to run counts as busy (an unreadable batch too); a
      `ResourceBusyError` at the build's lock is `busy`, not `failed`; a dry run prunes no lock registration
      (`live_users(prune=False)`); `--backend ""` is a usage error. Its known limit is documented: a change to
      `backends/shared` without a re-lock is not detected.
    - Digest effect: none (`cli/`, `update/`, `io/locks.py`, the GUI, packaging and tools are outside every stage
      scope; `regen_pins --check` passes). Tests: `tests/cli/test_frozen_sources.py`, `tests/cli/test_launcher_paths.py`,
      new cases in `tests/update/` and `tests/cli/test_backends_rebuild_stale.py`, `gui/tests/test_bundle_core_sources.py`
      and new cases in `gui/tests/test_updates.py` and `gui/tests/test_cli_launcher.py`.
