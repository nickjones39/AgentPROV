- **D-240 (2026-10-13, ingest-formats session: streaming `tar.zst`; user-approved 2026-10-13).** A
  zstd-compressed tar is read by D-57's framing parser (two passes, own 512-byte headers, no `tarfile`, the obs-G1
  long-name bound, the same member gate), now generic over the codec (`OpenedTar(codec=…)`), at level 1 (top-level
  container) and level 2 (member of a zip). `ingest/streams.py` `iter_zstd_bounded` parses each frame header with `struct`
  before a decoder exists: skippable frames and dictionary ids are refused (`ingest.stream.codec`: unverifiable), a window
  over `2**zstd_window_log_max` is `ingest.stream.memory`, a declared content size over the cap is `ingest.stream.size`;
  a fresh decoder per frame with `window_log_max` also set in libzstd; output bounded as it grows. Spec G.3.4/G.3.5
  "As built". Design: `docs/reports/ingest-formats/design.md` §2.
  - **Why:** Zenodo 20404563 (2,182 in-scope gemini-cli runs, D-143) and control-arena's batch logs ship as top-level
    `tar.zst`. Measured on the staged `RESULTS_raw.tar.zst` (user-approved read, 2026-10-13; in memory, nothing selected):
    one frame, window 2^23, no dictionary, 1,464,483,840 B decompressed, 75,577 entries including 1,642 GNU long names.
  - **Rejected:** `tarfile` with `r|zst` (it buffers long-name payloads, obs-G1, and has no window bound of its own);
    accepting skippable frames with a finding (their payload is never verified; no observed `tar.zst` writer emits them;
    `pzstd` does, and would be refused); deciding tar-ness from a profile flag instead of the first block (the magic-only
    rule of G.3.1 step 2 keeps one dispatch path); a top-level `tar.gz` (no source needs it; D-57's ruling stands).
  - **Effect:** `EXPAND_MODULES` (regen-batch `ingest-formats` bundle). A top-level zstd stream is now decoded up to its
    first block (after the header checks) to tell a tar from a deferred single stream; a corrupt or refused zstd frame
    raises its own code instead of `ingest.stream.codec`.
