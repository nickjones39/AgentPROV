- **D-28 (2026-10-11, the `dtap` adapter family: design rulings for DTap-Bench; phase 10b step 2, spec §D.16).**
  Recorded so that implementation (step 3) and review can check the design against its reasons.
  - (a) **Own family.** DTap gets a new family (`dtap.trajectory` reader and mapper, profile `dtap-bench`, catalogue
    `dtap` v1, semantics `dtap.tools@1`) rather than a profile of `agentdojo` or `inspect`. Its step log has no message
    list, no model-call boundary and no call ids, and its payloads live in a second dataset.
  - (b) **Identity.** The execution id is content-addressed (AD-04, D-27 c2). The logical identity is the path plus
    file stem; `task_info.task_id` and `trace_id` are never identity (both are non-unique), and the model and harness
    come from the path only.
  - (c) **Pairing is class I for all four harnesses, strict alternation included (D-24).** The logs carry no call id,
    so every pairing rule rests on how an unverified harness writes its log. The name check corroborates and never
    raises the class. Multi-call batches (8.6 % of results) are disclosed per batch.
  - (d) **Inferred model calls.** One `model_call` per maximal segment of agent steps (I), whose `input` is the logged
    prefix (I). The unlogged system prompt and tool descriptions are never input members; a logged tool list is a
    fixture referenced by `tools` (I).
  - (e) **Role `agent` is kept verbatim**, so the role-`assistant` accounting and typing do not apply.
  - (f) **Time.** `traj_info.timestamp` is the run end at class I (a statistical fit). The naive googleadk times are
    `end_naive` with `ambiguous`. Durations without a clock go to `ext` with `/t/dur_s` `ambiguous`. No start and no
    per-step time is computed.
  - (g) **Configuration join.** A deterministic path join and a deterministic tier (A, B, C). Configuration content
    describes a run only in tier A, and always at class I (never O). Id normalisations are applied only where
    evidenced, and only to the recorded `task_id` check.
  - (h) **Injection exposure.** A payload is *observed in the run* when a deterministic matcher (D) finds it in a field
    the run logs (tool output, logged tool-description list, logged user step); otherwise it is *configured only*, and
    every statement about it is class I. The configured payload entity, its attribution and its run membership are
    inference-bundle statements. The exposure claim (`dtap.exposure`, eight classes) is an assessment, as every
    exposure claim is (E.7.2), at class I for `configured_only`.
  - (i) **Judge evidence.** Recorded judge values are O; their `checker` origin is I (the judge code is not verified
    for the runs). `direct_prompt` `task_success` and benign null `attack_success` are `harness_default`.
  - (j) **Fixtures.** Configurations with `env_vars` are committed as derived fixtures, with their transformation and
    the original digest recorded. They are test inputs, never corpus raw.
  - **Why:** each choice states only what the files and the census support. Where the only premise is the behaviour
    of a harness whose code is unavailable, D-24 makes the statement an inference, and the observed/inferred line on
    exposure is exactly the line between text the run log holds and text only the configuration holds.
  - **Rejected:**
    - (a) a profile of the AgentDojo family: its reader, quirks and model-call rules assume message lists and ids.
    - (c) D for strict alternation: it would rest on unverified logging semantics. Name matching for claudesdk: its
      result names are unreliable. No pairing at all: that would discard 91.4 % of unambiguous links.
    - (d) one `model_call` per agent step: it asserts a turn boundary the log does not show. No `model_call` at all:
      it hides the agent's activity and removes the context premise of every engine exposure claim. Rebuilding the
      context with the configuration's system prompt: that is an unrecorded input.
    - (e) relabelling `agent` to `assistant`: D.15.1 forbids relabelling source fields.
    - (f) converting the naive times to UTC from the file-name stamp pattern: an inference presented as a time.
      `end − duration` as a start: a derived time over an unknown clock.
    - (g) a commit-date choice of configuration revision: no revision existed during any run. D for tier A: the
      revision in force is unverifiable.
    - (h) treating configured tool-description payloads as observed fixtures: that would hide the limitation D-26
      requires to be measured. Dropping them: that would hide it too.
    - (j) committing configurations with `env_vars` byte-identical: sandbox credential values would enter the
      repository. Omitting those configurations: it would lose the `direct_prompt`, control, multi-turn and
      medical-join fixtures.
  - **Addendum (2026-10-12, user delegated the decision): inferred times are never PROV times.** A time value whose
    reading is class I (e.g. DTap's `traj_info.timestamp` as the run end, D.16.18 item 1) stays in the AER verbatim
    (`t.raw`, with the I-class reading declared) and is available to `stats` and analysis, but `agentprov-prov/0.1`
    emits `prov:startTime`/`prov:endTime` only from O- or D-class times. The engine currently turns an I-class activity
    time into an inference-bundle entity carrying `prov:endTime`, which tier 4 rightly refuses (`PV-NE-6`). That path
    is a latent engine bug: no shipped corpus reaches it (every corpus passes tier 4). It is fixed by making the engine
    omit PROV time attributes for I-class times and raise a disclosed issue, with zero byte change to existing corpora
    (to be proven by the golden and compat gates); assigned to the regeneration-batch session as a small core fix,
    recorded here per invariant 5 (a correctness fix of the engine, not a change any adapter requires).
    - **Why:** invariant 2 forbids filling gaps, and a time whose meaning is only inferred is not evidence for a PROV
      timestamp; examination 2 (N7) already shows PROV activity times exist only where the source records them.
    - **Rejected:** letting the validator accept time attributes on inference-bundle entities (puts an unverified
      reading into PROV's temporal semantics and weakens PV-NE-6); typing the DTap time as D (D-24: the harness code
      that writes it is not verified).
    - **Implemented (2026-10-12, regeneration-batch session; invariant 5 record).**
      - **Change:** `prov/rules/nodes.py` `times()` skips a present `/t/start` or `/t/end` whose class is I. It writes
        no `prov:*Time` and no `apv:*TimeLexical`, and adds the disclosure `inferred_time_omitted` (`<rid>/t/<end>`) to
        the derivation report, never to the PROV bytes. E.5.3 item 7 says so.
      - **Zero byte change:**
        - No stored AER has an I-class time: 0 of the 218,412 present times of the phase-10 corpora (adprov-v1 164,888,
          AgentHarm 53,524; the other corpora carry none), and 0 in the earlier stored copies of both.
        - Nor do current mappings: 300 adprov-v1 executions re-mapped from raw with the current mappers give 0 of
          2,782. AgentHarm's mapping is byte-identical to the stored one (item 3).
        - The golden PROV/SEM pins and the frozen compat oracle are unchanged.
      - **Tests:** `tests/unit/prov/test_engine_tier4.py`: the `inferred_time` variant passes tier 4, and
        `test_an_inferred_time_is_never_a_prov_time` checks no end time in any bundle, the D start in the core
        bundle, the disclosure and tier 4. Both fail without the fix (PV-NE-6 / `pv.prov_structure`).
      - **Not done here:** DTap still writes its run end only as `t.raw.end` (D.16.18 item 1). Typing it as an
        I-class `t.end` is now safe, but it is an adapter change for the DTap session.
  - **Addendum 2 (2026-10-13, user-approved; regeneration-batch item 24; invariant 5 record): an inferred
    `unexecuted_tool_call` is pointed at.** When the seal issue `unexecuted_tool_call` cites a class-I rule
    (`dtap.call_without_result@1`; AgentOps' `agentops.fault_injection_unverified@1`, phase 10i README §9), the
    engine put `apv:dispatchStatus apv:NotDispatched` into an inference-bundle mention with no `apv:sourcePointer`.
    Tier 4 refuses that statement (`pv.linkage.pointer_missing`, `pv.linkage.basis_not_cited`), and it blocked
    555 in-scope AgentOps runs. The cause is an engine gap, not the mappings: the same issue under a D rule
    validates. The fix is a correctness fix of the engine and the linkage check, not a change an adapter requires.
    - **Change:** the issue is the attribute's premise. `prov/engine.py` gives it the field `seal/issues/<i>`, with
      the class and method of the issue's rule, and `validate/linkage.py` reads a pointed seal issue's `rule` as cited.
      Spec E.10 item 23 is amended.
    - **Rejected:** exempting the statement from the pointer check like `x:capture-profile` (it would still fail
      `basis_not_cited`, and the declaration is a single addressable premise); pointing at the request part (that
      record does not cite the rule); typing the adapters' rules D (the dispatch status is not recorded, so I is
      right).
    - **Zero byte change** to stored corpora and goldens: every stored `unexecuted_tool_call` cites a D rule, and a
      D attribute is a core statement without pointers. Proof: the golden, gate-D, C.16 and compat tests pass
      unchanged.
