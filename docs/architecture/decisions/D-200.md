- **D-200 (2026-10-12, deferrals part A: archive inputs; user-approved with the merge of part A).** A download pin's
  file (a Zenodo or Hugging Face file) whose members are whole run logs is an **archive input**: `import --input FILE
  --verify-against-pin` (or `--fetch` from the verified cache) stores the file with the pin's origin (`zenodo {doi,
  file}`, `hf {repo, revision, path}`), expands it in place through the versioned `expand` stage with the profile's
  `include`, `blobs` and context-artefact globs as the selection (AD-12; never extracted; members outside the selection
  are `not_selected` rows and are never decompressed), and maps every selected member as a whole file with its `member`
  origin. Register subjects of members are `<file>!/<member>`; the working manifest's snapshot records `input {kind:
  archive, label, sha256, bytes}`; `recompute` re-expands the stored container (`StoredRawTree.archive_input`); sealing
  builds the snapshot origin `{kind: zenodo, doi, file, md5?}` (H.2.3). An archive of a container dialect (an archive
  inside an archive) is refused (exit 5); a `.zip` under a git pin stays refused. The mapper side (the TraceLogger mapper
  reading the layout from a `member` origin's `label`, D-156 part 2) is the mapper owner's (D-204).
  - **Why:** every Zenodo source needs it (phase 10f's D-154/D-156, phase 10g's 23168099, phase 10i's AgentOps-Bench);
    the existing `expand` stage and its limits (SEC-05) already gate archive members, so no new parsing surface is added.
  - **Rejected:** a separate "archive tree" walk parsing the central directory in T0 (archive parsing belongs in T1,
    G.4); registering every `not_selected` member (its `raw/members.jsonl` row is its disposition, R-40); member
    subjects without the container prefix (a re-map could not tell them from the container's own rows).
