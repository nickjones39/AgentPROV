- **D-893 (2026-10-28, `validate --corpus --jobs N` stages the next batch while the pool runs the current one; M5 Ultra
  performance round 2, item 1b).**
  - **Finding.** The pooled validate (D-413) alternated. The parent read, verified and staged a 256-row batch while the
    pool sat idle, then waited for the pool. At `--jobs` 3–4 the parent averaged ~0.5 CPU, and `--jobs 16` was no
    faster than `--jobs 8`.
  - **Change.** As `derive` does, the next batch is read and staged while a background thread runs the previous batch's
    jobs. Rows are still recorded in index order.
    - Staged inputs are reference-counted, so bytes two batches share are removed only when the last of them is
      recorded.
    - A cache entry stored by one batch can reach the next batch's rows one batch later. It is a hint the job
      re-checks (D-550), so this affects timing only.
  - **Measured** (`ast-survey-agentdojo-rg2`, 3,243 executions, main's code before against after; every report has
    byte-identical rows):

    | Point | Before | After | Change | Conditions |
    |---|---|---|---|---|
    | `--jobs 8` | 43.5 s | 31.5 s | −28 % | exclusive window, machine CPU 3–5 |
    | `--jobs 16` | 46.7 s | 37.0 s | −21 % | exclusive window |
    | `--jobs 4`, quietest pair | 58.8 s | 35.3 s | −40 % | load 11–13 |

    - The parent's mean CPU rose from 0.59 to 0.95.
    - A `--jobs 4` pair at load 28–32 gave 223.9 s against 101.3 s. One pair was discarded: the "after" run found
      the tier-4 cache cold (see D-894).
  - **Rejected:** more rows per batch with no overlap. It only shortens the barrier.
  - **Class 0:** `corpus/validation.py` is outside every stage scope.
