- **D-610 (2026-10-21, an import that stops early is recorded incomplete; found by the new-families bug pass while
  building its NF premerge, confirmed and designed by the CLI robustness session; user decision 2026-10-21, option 2
  "run-state mark", given in the orchestrator's window and relayed by it; regen item 150; branch
  `integration-incomplete-mark`).**
  - **Finding (reproduced on integration head b8d144cb):**
    - A fresh import with no selection that is drained (D-394) after 2 of 4 candidates recorded `partial: false`, no
      selection and `limit: null`. `package._check_working` took it for complete.
    - So did one interrupted by a first SIGINT, SIGTERM, SIGHUP or `stop`, or by any error. `import_source`'s `finally`
      flushes and writes `corpus.json` from the selection alone. That predates the drain (R-10k-1 and the Part A
      SIGHUP flush).
    - A run killed outright (SIGKILL, the second signal's `os._exit`) writes nothing. The index is flushed only at the
      end, so a fresh corpus has no manifest and an existing one keeps its previous manifest and rows. It was "accepted"
      only when a resume of it was itself drained or interrupted.
    - Snapshot `counts` show the gap only for single-execution sources (candidates count files), so they cannot be the
      guard.
  - **Decision:**
    - **The mark.** A run that stops before it ran to the end marks the snapshot it was importing
      `incomplete: {"reason": "drained" | "interrupted"}` and the corpus `partial` (MN N.1.7, N.1.10(2), (3), (5); HL
      H.2 working manifest).
      - `drained`: a D-394 drain.
      - `interrupted`: `run` raised.
      - **No mark where a cap describes the stop.** A drained run whose snapshot then records NF-36's cumulative cap
        (`limit` = the units held), and whose cap is accurate, is described by that cap. The cap is accurate for a
        drain that mapped from the source (not `--until raw`, not a re-map), is not a completion of a snapshot with a
        filter or sample (NF-36 keeps that selection although the run mapped units outside it), and has a clean tail:
        its last mapped candidate, in candidate order, ended in a unit the cap counts: its last unit is non-degenerate,
        for a whole file, a multi-execution file or a container member alike (second review below). Such a
        snapshot stays partial through its selection, and a re-map maps the same units. An earlier mark is kept
        whatever cap a later stopped run records.
      - **Review amendment (2026-10-21, NF pass on integration head d559ce6a).** The first narrowing (any stopped run
        whose cap is accurate by the conditions above, without the drain and clean-tail conditions) let three
        reproduced cases through unmarked, and a real `agentprov recompute` of each exited 1 with unexplained origin or
        register rows. The setup was agentdojo, 4 logs, `--batch-size 1 --limit 10`, stopped at the first `unit_done`:
        (1) a drain after a degenerate unit, which the non-degenerate cap does not count; (2) a drain after a rejected
        candidate (broken JSON: register and origin rows, no unit); (3) an interrupt with clean data, where the next
        batch was mapped and stored but never indexed, because mapping runs a batch ahead. Root cause: the cap counts only
        non-degenerate indexed units, so a re-map stops right after the last counted one. Fix: only a drain can be
        described by its cap (an interrupt is always marked), and only with a clean tail. NF-36's interrupted-cap test
        now expects the cap and the mark. The clearing rule is unchanged.
      - **Second review (2026-10-21/22, NF pass on e960c64a, probe 5).** The first tail rule accepted a container or
        multi-execution candidate holding any counted unit. But the cap counts units, and a re-map cuts per unit inside
        a file. A drained credleak-shaped JSONL archive whose last mapped file ended in a degenerate item after a counted
        one (a1=[ok], a2=[ok, degenerate]) held a1#0, a2#0 and a2#1 with cap 2 and no mark. An unstopped `--limit 2`
        records the same cap and holds a1#0 and a2#0. Fix, one rule for every kind: the last unit is not degenerate and
        belongs to the batch's last candidate: its own label, or a member of it (`label + "!/"` as a prefix, since a
        container inside an archive input has `!/` in its own label; a third review replaced a first-segment split that
        cut such a label). Job-level register rows and dedup members repeat in a re-map and need nothing extra.
    - **Clearing.** A later run of that snapshot clears the mark once it has run to the end with nothing left to map:
      it mapped (not `--until raw`), and it had no `--limit` or found fewer units than its limit. That is the same
      command re-run, with the same selection or none; NF-36's identity check refuses any other.
      - A `--limit` run that stopped at its cap with units left keeps the mark. The cap it records need not describe
        what the stopped run held: after a drained uncapped snapshot, NF-36 records no cap for a later limit.
      - A run of another snapshot never clears it.
    - **Refusals.**
      - `package` refuses a marked corpus before its partial check, so the refusal names the cause (exit 4,
        `package.refused.incomplete`), and refuses whatever the corpus-level `partial` says.
      - `derive` and `recompute` refuse it as their source in `resolve_plan` (exit 4, `corpus.derive.incomplete`):
        a re-map would map what the raw store holds, not what the corpus holds.
      - `verify --level rederive` reports the re-derivation as unavailable, as for any plan refusal.
    - **Summary and log.** A drained import's summary carries a notice naming the snapshot, the reason and how to
      complete it; the run that clears a mark says so. An interrupted run returns no report, so it logs a warning; the
      CLI's interruption notice names the signal as before. `ImportReport.incomplete` lists the marked snapshots.
    - NF-36's cap logic is unchanged for real `--limit` runs.
    - A corpus no run stopped carries no mark, so an ordinary manifest is byte-identical.
  - **Rejected:**
    - Recording a drained or interrupted new snapshot as `limit = indexed`, the NF bug pass's first suggestion:
      - it writes a `--limit` the user never gave, a fabricated selection against invariant 2's spirit;
      - a cap describes only a prefix: an interrupted completion of a filtered or sampled snapshot holds units outside
        that selection, and a drained sampled new snapshot would record the sample uncapped, so a re-map would hold
        more or fewer executions than the corpus.
    - Inferring completeness from the snapshot counts (wrong for containers and multi-execution files).
    - Clearing the mark with a `--limit` run that reached its cap.
    - Letting `validate` clear it (validate stays read-only, as for G2c-5).
  - **Byte class:**
    - `adapters/runner/importer.py` is in the `aer` stage's code digest, so the `aer` `engine_code_sha256` moves for
      imports made afterwards (class 1, regen item 150; item 130 moves the same digest).
    - `corpus/runstate.py` (new), `corpus/package.py`, `corpus/derive.py` and `cli/import_.py` are outside every stage

    - No AER, SEM or PROV bytes change. `corpus.json` changes only for a working corpus a run left incomplete; the

  - **Existing corpora:** a working corpus left by an earlier drained or interrupted run cannot be detected afterwards,
