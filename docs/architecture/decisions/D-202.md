- **D-202 (2026-10-12, deferrals part A: several snapshots per corpus; resolves the spec drift of D-64; user-approved with the merge of part A).** One
  corpus may hold several snapshots of its one source through one source profile (H.1.1(1)): a later `import` into the
  same working corpus with another `--snapshot` adds it (G4 still refuses another corpus id, source, mode or profile).
  H.7.2 is implemented: a primary artefact another snapshot already mapped is not mapped again; its row lists the new
  snapshot in `snapshot_ids`, its new origin is a `raw/origins.jsonl` row (`n_origins` recounted), and a
  `dedup.collapsed` entry records it. The AER of a shared execution carries the origin of the snapshot that imported it
  first; the manifest keeps the snapshots in import order (each with its `part` once there are several) and `recompute`
  and `verify --level rederive` replay them in that order, each from the objects its pin vouched for
  (`origin_matches_pin`), so a re-map is byte-identical. Sealing takes each snapshot's origin from the origins its pin
  vouched for. **D-35 stands:** `agentdojo-upstream` is released as two corpora; a one-corpus, two-snapshot AgentDojo
  tree is a supported layout used for scratch comparisons. Spec: H.4.2's `agentdojo-upstream` row, H.7.2, N.2.2's
  `--snapshot` row and N.2.2(7) are reconciled to this.
  - **Why:** the user asked for the refusal to be lifted; H.7.2 is the spec's own rule, and D-35 is a release decision,
    not a format limit.
  - **Rejected:** re-sealing earlier AERs to a canonical snapshot order (rewrites sealed records); origin-free AERs (an
    `aer/0.1` change); corpus-scoped execution ids (rejected in D-35 too).
