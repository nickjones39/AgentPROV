- **D-39 (2026-10-11, `verify --root-digest sha256:…`; phase 11).** The option (repeatable) takes a root digest
  published outside the corpus (tag annotation, paper, deposit record) and compares it with
  `"sha256:" + sha256(checksums.sha256)` (H.5.4) at every level; in archive mode each digest must equal one corpus's.
  A difference is `root_digest.mismatch` (exit 1); a working tree cannot match (`root_digest.unverifiable`). `verify
  --release` in tree mode or on a lone meta archive requires it (exit 2 otherwise); a deposit is anchored by its
  manifest, where the option stays the only defence against an end-to-end consistent forgery. **Amended by D-620
  (2026-10-22):** a deposit manifest anchors nothing, so `verify --release` on a deposit directory requires it too.
  The computed root digest is printed after every run and never written into the corpus. Details:
  `docs/reports/phase11/decisions/D-39.md`.
  - **Why:** a regenerated `checksums.sha256` over files no digest chain covers (`DATASHEET.md`, `CHANGELOG.md`,
    `LICENSES/**`) is detected only by a digest kept outside the tree (K.12.5).
  - **Rejected:** reading the expected digest from inside the corpus or deposit (circular); requiring it in dev mode;
    bare hex digests; treating a mismatch as `unverified`.
