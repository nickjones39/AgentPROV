- **D-870 (2026-10-28, addendum to D-790 and D-800: `tools/zenodo_draft.py` gains communities, a reserved DOI recorded in
  the receipt, and a drafts-only cross-link step; the user approved the design in the session window).** The user decided
  (2026-10-28) to release the corpora as several Zenodo records, one per licence class (with splits under the per-record
  limits), gathered in one Zenodo community, cross-linked to an umbrella record. The pre-release checks found two gaps in
  the helper: it set no community, and it neither reserved nor recorded a DOI the other records could point at.
  - **Communities:** a repeatable `--community SLUG` option (a Zenodo community identifier: lower-case letters, digits,
    `-`, `_`), shown on the consent screen and sent as `metadata.communities = [{"identifier": SLUG}]`, the shape of the
    REST documentation (read 2026-10-28 with the user's yes). Each community's curators accept or decline the request.
  - **Reserved DOI:** the DOI comes from `metadata.prereserve_doi.doi` (and `.recid`) of Zenodo's answers.
    `prereserve_doi: true` goes with the metadata `PUT` only while no reserved DOI is known. The trial of D-800 saw
    drafts that already carried one, so on the sandbox no request is expected. Every later answer must carry the same
    DOI; otherwise the run stops (`failed:reserved_doi_changed`). A metadata `PUT` whose answer has no DOI stops the
    run before any upload (`failed:no_reserved_doi`). `--resume` reads the DOI back and asks for none while one is
    recorded. It refuses a run whose metadata (with its `--community` options) differs from the receipt's.
  - **Receipt `agentprov-zenodo-draft-receipt/0.2`:** the 0.1 fields plus `reserved_doi`, `reserved_recid`,
    `communities`, `metadata` (the exact object sent, without `prereserve_doi`) and `cross_links`. It is a new version,
    and 0.1 is unchanged. A 0.1 receipt is still read, so it still blocks a second create, but `--resume` and the
    cross-link step refuse it because it records no DOI.
  - **Cross-link step:** `--cross-link --umbrella RECEIPT --member RECEIPT ...` (no deposit directory). After a screen
    that lists each draft, its DOI and the links to add, and the typed phrase `link N unpublished drafts on HOST`:
    - **The links:** each member gets `isPartOf` the umbrella's reserved DOI, and the umbrella gets `hasPart` each
      member's. The recorded metadata is `PUT` again with the links appended, each pair once, so a re-run changes
      nothing.
    - **Read-back:** each draft is read back, and its links and DOI are checked.
    - **Read before writing:** every deposition is read before any is written.
    - **Refusals, with nothing written:**
      - a receipt that is 0.1, records no reserved DOI, is not `complete`, or belongs to another target;
      - a receipt given twice, the umbrella listed as a member, or two receipts naming one deposition or DOI;
      - a published deposition, or one in an unknown state;
      - a reserved DOI on the server that differs from the receipt's;
      - related identifiers on the draft that the tool did not send.
    - **No new request kind:** the step uses only the `GET` and `PUT` of depositions that are already allowlisted.
  - **Rejected:**
    - `communities` in `release.toml` and `deposit-metadata.json` (`agentprov-deposit/0.2`), for now. That is a change
      to `agentprov.release`, a class-1 format bump. A community is a Zenodo placement, not corpus metadata. It remains
      possible later if the user wants it sealed.
    - Sibling links between members (`isRelatedTo`): this relation is not in the deposit API's vocabulary (the
      helper's `ZENODO_RELATIONS`, and the documentation read 2026-10-28). The members are linked through the
      umbrella.
    - An umbrella given only by DOI: the umbrella is a helper deposit like the others (the user's choice), so it also
      gets `hasPart`.
    - Sending `prereserve_doi: true` on every `PUT`: it is a reservation request, and none is needed once a DOI is
      recorded.
    - Asking for the reservation in the create `POST`: its body `{}` is the request the trial verified.
  - **Not yet trialled:** none of the new requests has been sent to the sandbox: the `communities` field, `prereserve_doi:
    true` on a draft without a DOI, a metadata `PUT` without `prereserve_doi` that keeps the DOI, and `isPartOf`/`hasPart`
    to reserved, unregistered DOIs. The user runs `tools/zenodo_collection_trial.sh` in their own terminal; the report is
    `docs/reports/release/zenodo-sandbox-trial.md`.
  - **Byte class 0:** `tools/`, tests and docs only; no file of any stage scope changes.
