- **D-414 (2026-10-14, pipeline-perf; reviewed by the runner, deferrals and ingest-formats-3 sessions; user-approved
  2026-10-14 with regen-batch item 42).** The parent holds the frames of worker results as bytes, not as decoded
  objects.
  - **Storage:** every `JSON` frame is still parsed and checked on arrival, then kept as its bytes (`_Payload`), in
    memory while the job's `SPOOL_MEMORY_PER_JOB` and the pool's `SPOOL_MEMORY_PER_POOL` (256 MiB) allow, otherwise in
    one spool file per `WorkerPool.run` batch.
  - **The spool file:** opened on the first spill, unlinked at creation, `pwrite` under a lock, `pread`-only reads,
    refcounted and finalized, so a consumer that raises mid-batch leaks nothing. Members above
    `MemberOutput.SPOOL_MAX` (now 1 MiB) or over budget are ranges of the same file: one descriptor per batch.
  - **Two passes:** the importer reads a `map` result in two passes (`summarise_unit_frames`, then
    `iter_unit_frames`). The whole-file, per-item, container and live-session paths keep the D-321/D-323/D-218 order
    and the same raises. `JobResult.json` is always memoised, and the per-item and container paths never use it.
  - **Effect:** parent RSS 1,191 → 674 MiB on a 7,200-execution synthetic multi-execution deposit.
  - **Identity:** byte identity on that deposit, Mandate and a ROPE subset. The only change is the aer stage's code
    digest (item 42).
  - **Design and results:** `docs/reports/pipeline-perf/parent-frames-design.md`, `results.md` §5.
  - **Rejected:**
    - sealing units as frames arrive (a later `abort`, `register` row, `FAIL` or carved-blob decision changes the
      file's fate);
    - a descriptor per result (EMFILE at the macOS default of 256);
    - raising the parent's soft `NOFILE`;
    - a per-job budget only (a 256-result batch could hold 16 GiB).
