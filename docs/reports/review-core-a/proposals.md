### Items routed to regen-items (it owns `adapters/agentdojo/`)

- **Item 77, CA-19: a null text block renders `text: null`.**
  - Current behaviour, `adapters/agentdojo/mapper.py` `_content_parts`: a TraceLogger assistant content list with one
    `{"type": "text", "content": null}` block (or with `content` absent) maps to `{"t": "text", "text": null}`. That
    is byte-identical to the D.6.6 encoding of `content: null`.
  - `views/transcript_v1.py:589-592`: the view's `null_content` test (exactly one text part, whose text is null) then
    renders `"text": null`. The converter rule gives `""`.
  - Only `agentdojo.mixed_content_forms` is raised, and only when the file mixes forms. A file entirely in blocks
    form raises nothing.
  - Proposed change: when a text block's content is null or absent, the mapper records the part index in
    `ext.agentdojo.null_text_blocks` (a list of ints, under the closed `ext.schema.json`). The view's `null_content`
    test skips a message that has `null_text_blocks`. Add a D.6.6 parts-layout row ("a text block with null/absent
    content → `{t:text, text:null}`, index in `ext.agentdojo.null_text_blocks`").
  - Stored bytes: AER changes only for messages with such a block; views change for them too (`""` instead of
    `null`). D.6.11 item 4 reports none in head v1.k14 logs.
  - Repro: `repro/CA-19_A2b-7/test_repro.py.txt`; proposed diff `fix.diff.txt`.
  - Alternative: encode the null block as `text: ""` with `unk` `ambiguous`. Rejected, because it invents a value the
    source does not hold.
- **Item 78, CA-11 (agentdojo copy): the family checker's enum treats `true` as `1`.**
  - `adapters/agentdojo/profile.py:114` repeats the `value not in schema["enum"]` comparison that CA-11 fixed in
    `io/jsonschema_subset.py` (7dbce006).
  - The family checker validates trusted package data (`family.schema.json` against the source profiles), and every
    enum there is string-valued, so it is latent.
  - Proposed change: re-export `io.jsonschema_subset`'s `_json_equal` comparison (or the whole checker, as the
    `io/jsonschema_subset.py` docstring anticipates), and add the boolean-vs-number enum case to the family checker's
    differential test.
  - Stored bytes: none (only `adapter_code_sha256` moves).

## Decision proposals (decided 2026-10-14: option 1 of each; D-500, D-501 in `DECISIONS.md`)

Both decisions concern the published vocabulary `apv-0.1.ttl` (apv 0.1.0, `owl:versionIRI …/ns/0.1.0`). E.4.6 item 2
sets the version rule:
- patch: documentation only;
- **minor: adds terms**;
- **major: changes meaning or removes terms**.

Once 0.1.0 is released, terms are never deleted; they are deprecated instead. Every PROV document states the version in
`apv:vocabularyVersion` on the derive activity, so any bump changes every stored PROV document. Both decisions can go
in the same bump.

### D-500 (CA-21). Data properties that the engine fills with `apv:RecordedNull`

**Problem.**
- E.5 item 5 turns an asserted JSON null into the QName `apv:RecordedNull`. It names task ids and `error` explicitly.
- `apv-0.1.ttl` declares `apv:error` (l.1151), `apv:taskId` (l.1442), `apv:defenceId` (l.1463) and the other
  attributes routed through `opt()`/`lit()` (`finishReason`, `servedModel`, `requestedModel`, `toolName`,
  `outcomeValue`, `reason`, …) as `owl:DatatypeProperty; rdfs:range xsd:string`.
- The engine nevertheless writes `… apv:error apv:RecordedNull`, an IRI object of a data property. That is not
  OWL 2 DL; under RDFS it entails `apv:RecordedNull rdf:type xsd:string`.
- Shipped mappers emit these nulls routinely: adprov `defense_id`, a tool result `error` on success, agentdojo
  without a defence, and credleak `attack_id`.
- `tests/unit/prov/test_vocab.py::test_qname_valued_properties_are_object_properties` shows the intended typing
  discipline.

**Options.**
1. **Status siblings (recommended)**, minor bump, **apv 0.1.0 → 0.2.0**.
   - Add one `apv:<prop>Status` object property per affected data property, following the existing
     `apv:contentStatus` pattern (E.4.5). The engine emits `<prop>Status apv:RecordedNull` and omits the data property
     when the value is null.
   - Existing terms keep their meaning, so this is additive.
   - Stored bytes: every PROV document and its digest (`vocabularyVersion`, and the null triples). The compat
     oracle is unaffected, since it has its own `adprov.ttl`.
   - Code: `prov/rules/nodes.py` and `vocab/apv-0.1.ttl` → `apv-0.2.ttl`, plus `docs/ns/` and the `versions.py`
     `"ontology"` axis.
2. **Weaken the ranges**, major bump, **apv 0.1.0 → 1.0.0**.
   - Re-declare the affected properties as `rdf:Property` with no `xsd:string` range, and document the RecordedNull
     convention in their `rdfs:comment`.
   - The emitted triples stay the same, but the meaning changes, so E.4.6 requires a major version.
   - Stored bytes: `vocabularyVersion` in every PROV document.
   - It also gives up OWL DL typing for these attributes.
3. **Keep as is and document the deviation** (no bump, no bytes).
   - Record in E.5 item 5 that RecordedNull is an IRI on data properties, a known OWL DL violation.
   - Rejected by this review: published vocabulary and documents that contradict each other are what E.4.6 item 2
     says "MUST NOT recur".

### D-501 (CA-22). `apv:assumption` range against string adapter assumptions

**Problem.**
- `apv-0.1.ttl:761-766` declares `apv:assumption` as an `owl:ObjectProperty` with `rdfs:range apv:Assumption`.
- E.10 item 11 and D-17 require adapter-declared assumptions (`rope:…`, `agentdojo:…`, `agentops:…`) to be strings,
  because documents declare no adapter prefixes. `prov/engine.py:955` does exactly that.
- So the engine follows the spec, and the vocabulary contradicts the documented output: 15 triples on the C.16
  vectors alone.
- A consumer that queries `?a a apv:Assumption`, or that checks the declared range, misses or rejects every adapter
  assumption.

**Options.**
1. **Sibling data property (recommended)**, minor bump, **apv 0.1.0 → 0.2.0** (the same bump as D-500 option 1).
   - Add `apv:adapterAssumption`, an `owl:DatatypeProperty` with `rdfs:range xsd:string` whose comment gives the
     `<ns>:<Name>` form. The engine emits core assumptions on `apv:assumption` and adapter ones on
     `apv:adapterAssumption`.
   - E.10 item 11 and D-17 stay as they are; E.1.5 item 4 and the linkage validator (`apv:assumption` on INFERRED
     statements) are extended to the new property.
   - Stored bytes: every PROV document with an adapter assumption, plus `vocabularyVersion`.
2. **Declare adapter prefixes and emit QNames** (no vocabulary change for the range).
   - Each adapter catalogue namespace gets a declared PROV-JSON prefix, and adapter assumptions become
     `prov:QUALIFIED_NAME` like core ones.
   - This reverses E.10 item 11 and D-17. It needs a stable namespace IRI per adapter (w3id placeholders, U-02) and
     the adapter individuals typed `apv:Assumption` somewhere.
   - Stored bytes: every PROV document with an adapter assumption.
   - apv itself needs no bump, but the prov spec does (`agentprov-prov/0.1` → `/0.2`: an output-format change).
3. **Weaken the range**, major bump, **apv 1.0.0**.
   - Make `apv:assumption` an `rdf:Property` without a range, and document that adapter values are strings.
   - The emitted triples stay the same.

**Recommendation:** decide D-500 and D-501 together as option 1 of each, which makes one minor bump to apv 0.2.0
(additive only). Both land in the regeneration round, so every PROV document is rewritten once. Two implementation
items would be reserved when the decisions are taken.
