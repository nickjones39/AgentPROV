  - a degenerate unit under a redacted arm holds no account.
- **Order fix (pre-round review #7, branch `integration-fix-108`).** The hold now runs after RD-3's `pin_candidates`
  snapshot. A listing pin covers the whole selected listing, so a held file that is missing from it would make every
  other file `raw.origin.blob_mismatch`. The held file is still registered and never imported. This was latent: only
  adprov-v1 has a listing pin, and no label of it is account-shaped. Test:
  `test_a_held_file_stays_in_the_listing_a_listing_pin_is_checked_against`, which fails before the fix. Prediction:
  the aer stage `engine_code_sha256` moves for every family (`adapters/runner` is in its D-451 scope), as with item
  108 itself. No stored byte moves.
- **Coverage fix (pre-round review #19, same branch).** `covered()` counted any pattern match anywhere in the
  account's segment as cover, and ignored a rule's `labels` allowlist. So D-607's dtap `host_account_token` (a match
  on every token) made the lint vacuous under dtap-bench@2. A rule now covers an account only when:
  - one of its matches in that segment includes the account token (its `span` group, else the whole match);
  - for a rule with `labels`, the span's `{span12}` label, salted with the profile id, is listed.

  `account_shapes` keeps the token in memory for this check only, never in a report or row. Tests: a match that misses
  the account, and a listed versus an unlisted label (and the wrong salt).
  - **Measured:** the only account-shaped labels in any staging clone are EnvironmentOptim's, and its rule still
    covers them. No file is newly held, and no stored byte moves. `account_paths.py` is outside the stage scopes, and
    the importer's one-argument change moves the aer engine digest only with the order fix above.
