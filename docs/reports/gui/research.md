# AgentPROV desktop GUI: research report

Status: the research behind D-390–D-399, which were approved as the direction on 2026-10-14. Branch `gui-research`
from origin/main `c4fd0dc2`. No application code was written. The design that follows from this report is
[`design.md`](design.md); its decisions are D-390 to D-399 (in `DECISIONS.md`). This report answers the twelve research questions in order (Q1–Q12). Each answer gives the evidence, an
options comparison where there is a choice, a recommendation and the rejected alternatives. The local measurements are
in §M and the sources in §S.

### Q1.2 Findings per criterion

- **Cross-platform fidelity.**
  - Qt draws native-looking widgets on all three OSes (the macOS native style; Fusion on Windows and Linux).
  - Qt's blog recommends **Fusion** as "our preferred style for Windows 11" for dark mode under Qt 6.5+ [S9]. A
    `windows11` style in Qt ≥ 6.7 is reported only by a secondary source (*unverified*), so the design uses Fusion on
    Windows and Linux and the native style on macOS.
- **Python 3.14.**
  - PySide6 6.10.1 is the first release with "Python 3.14 is now supported". 6.10.0 still declared `<3.14` [S1].
  - 6.12.0 wheels are `cp310-abi3` for macOS 14+ universal2, glibc 2.34+ x86-64 and 2.39+ aarch64, and Windows x86-64
    and ARM64 [S1].
  - **There are no free-threaded (`cp314t`) PySide6 wheels**, so the GUI runs on the GIL build of 3.14. The core is
    unaffected.
  - Locally, `PySide6-Essentials` 6.12.0 installed on CPython 3.14.8 and every benchmark ran (§M).
- **Licence (LGPL obligations).** Qt's LGPLv3 obligations page [S2] requires:
  - the complete corresponding Qt source (or a written offer), even if Qt is unmodified;
  - dynamic linking (recommended);
  - that users can change, relink and run the relinked app;
  - installation information (no tivoisation);
  - the licence texts and a prominent notice.

  Two further points:
  - **Qt Charts, Qt Graphs and Qt Data Visualization are GPLv3 only** (in PySide6-Addons) [S3]. The GUI depends only on
    **`PySide6-Essentials`**: the System tab draws its sparklines with `QPainter`, not QtCharts.
  - PyInstaller **one-folder** bundles keep Qt's shared libraries replaceable. One-file bundles unpack to a temporary
    directory at each start, and whether that satisfies "able to relink" is a legal judgement (*unverified*), so they are
    avoided.
- **Install size.**
  - PySide6-Essentials 6.12.0 wheels: macOS universal2 116.0 MB, Windows x86-64 82.2 MB, Linux x86-64 84.3 MB. Addons
    add another 36–91 MB [S1].
  - Installed locally: 348 MiB unpacked (universal2, including QtQuick/QML frameworks that the bundle excludes).
  - No primary source gives a typical PyInstaller bundle size for a Widgets-only app (*unverified*). Excluding
    QtQuick/QML, QtNetwork, QtPdf and similar modules is the main lever (design §13).
- **Packaging per OS.**
  - **PyInstaller 6.22.3** (2026-09-12) supports 3.8–3.15 under GPLv2+ with a bundling exception.
    - It ad-hoc signs by default; `--codesign-identity` plus hardened runtime are available, and `--osx-entitlements-file`.
    - Notarisation is a separate `notarytool` and staple step [S4].
  - **Briefcase 0.4.6** builds `.app` with notarisation by default, MSI, and Linux packages or Flatpak; its maintainers
    discourage AppImage [S5].
  - **Nuitka 4.2** made 3.14 official, but its PyPI licence is AGPLv3+. Whether compiled output is covered by an
    exception is *unverified* [S6].
  - **`pyside6-deploy`** wraps Nuitka 4.1.1 by default; from 6.12 its default mode is standalone [S7].
  - Recommendation: PyInstaller one-folder builds (design §13, D-399). Nuitka or pyside6-deploy only after its licence
    terms have been read.
- **Accessibility.**
  - Qt implements accessibility for its own widgets on all three platforms (UIA on Windows since 5.11, NSAccessibility,
    AT-SPI over D-Bus) [S8].
  - `QGraphicsItem`s are not accessible objects, so the graph needs a parallel "Elements" list (design §12).
  - Tk 8.6 has none. Dear PyGui/ImGui has none (upstream issue #4122 open since 2021). Toga has open issues.
- **Large tables.**
  - Qt model/view asks the model only for visible cells. `fetchMore`/`canFetchMore` support incremental population [S8].
  - Measured locally (§M5): paint cost is **constant in the row count** (10k and 1M rows draw in the same time). A
    Python `QAbstractTableModel` over in-memory tuples sorts 100k rows in 86 ms and 1M in 0.5 s when sorting is done
    *in the model*.
  - **`QSortFilterProxyModel` over a Python model is ~100× slower** (5.4 s for 10k rows), because every comparison
    calls Python `data()`. The design forbids it over Python models.
  - Tk's Treeview has no virtual mode [S10]. Toga's Table was slow at 20 columns × tens of rows (#2744) [S11].
- **Theming:** see Q11.
- **Hidden web views and servers.** These were checked explicitly:
  - Tauri, Electron and pywebview embed web views.
  - NiceGUI is a server; Flet is client/server.
  - Textual's `serve` and textual-web are servers.
  - Toga ships an opt-in WebView widget.
  - Qt has QtWebEngine (not in Essentials; Addons only).

  The GUI bans QtWebEngine, QtQuick/QML and QtNetwork by a static test and a bundle-content check (design S11, §13).

### Q1.3 Recommendation and rejected alternatives

**PySide6 6.12, Qt Widgets, `PySide6-Essentials` only** (D-390).

Qt Quick/QML is rejected:
- QML `Text` defaults to `AutoText` like `QLabel`.
- Qt's own advisory for CVE-2025-12385 (an `<img>` size flaw in the Qt Quick text parser) says to set PlainText
  explicitly [S12].
- It adds QtQuick and QML deployment weight and gives nothing for 100k-row tables or the graph canvas.

The other rejections are in the table: PyQt6 (GPL), Tkinter (accessibility, no virtual table), Dear PyGui
(accessibility), Toga (tables, no graph canvas), Slint (beta, licence terms), and Tauri, Electron, pywebview, NiceGUI and
Flet (web view, server or client/server).

**Textual** is noted as a later, optional **terminal** companion that reads the same progress files over SSH on the Mac
Studio. `textual serve` and textual-web stay prohibited (design §15, "later").

## Q2. Architecture

### Q2.1 Structure

- The structure is MVVM / presenter (design §2.3):
  - a typed **read model** with no Qt, built on the core's strict readers (`CorpusReader`, `strict_json_loads`,
    `iter_jsonl` under `IngestLimits`);
  - services with no Qt (job manager, followers, layout, keychain, estimator);
  - Qt view models (`QAbstractTableModel` / `QAbstractItemModel`) that sort and filter in the model;
  - views built only through a safe-widget factory.
- **Coupling.** The GUI is its own uv project `gui/` and depends one-way on `agentprov` through an allowlist of
  read-only modules. Reasons:
  - It must use `quote_untrusted` / `escape_untrusted_line` (G.8.2) and `render.graph.build_model` (pure; no pydot).
    Re-implementing them would split the display-safety rules.
  - The core must never import the GUI. This becomes a new rule in `tests/boundary/test_import_boundary.py`, which
    already enforces analogous rules for `capture/` and `backends/`.
- **Writes** are only `agentprov` subprocesses. The CLI is the single engine and keeps every guard:
  - G1 sealed, G2 disjoint, G3 git, G4 identity, G5 mixed config, G6 lock;
  - release mode and the interpreter floor;
  - resume rules;
  - `--allow-network`;
  - consent and containment for paid runs;
  - withholding.

### Q2.2 Job manager over CLI subprocesses: findings that shape it (CLI inventory)

- **Signals.**
  - The CLI traps SIGINT and SIGTERM: the first one raises `KeyboardInterrupt`, the command flushes or seals, releases
    the lock and exits 130; a second one is `os._exit(130)` (`cli/common.py:546-580`).
  - **SIGHUP is not handled.** A job that shares the GUI's terminal session would die without a flush and leave a stale
    `.agentprov.lock`. For `import`, the index rows since the start would be lost.
  - Jobs are therefore started in their **own session** (POSIX `start_new_session`; Windows `CREATE_NEW_PROCESS_GROUP |
    DETACHED_PROCESS | CREATE_BREAKAWAY_FROM_JOB`), with stdout and stderr to files and no pipes.
- **Stdin and TTY.**
  - `run`'s consent prompt needs a TTY on stdin and stderr; under a GUI it exits 4 unless `--i-consent-to-api-costs` is
    given (`run.py:_consent`).
  - `purge` needs `--yes` when not interactive.
  - The GUI therefore owns the confirmations and passes the flags only after its own dialogs.
- **Resume.** Every writer is idempotent and resumes from `DIR.partial`:
  - import skips units with index rows;
  - derive and recompute resume `NEW.partial`;
  - run resumes from the per-attempt ledger, with `--max-attempts` counted across invocations.

  "Resume" in the GUI is therefore "re-run the same argv".
- **Locking.**
  - `.agentprov.lock` (`{pid, host, command, started}`, `O_EXCL`) covers `run`, `import`, `derive`, `recompute --out`
    and `purge`.
  - **No lock covers the fetch cache, backend environment builds or `$AGENTPROV_HOME/staging`.** The GUI serialises
    those itself (design §4.4).
- **Graceful stop on Windows.** `SIGTERM` on Windows is `TerminateProcess`, which is not graceful, and the CLI does not
  handle `SIGBREAK`. A cross-platform **control file** is therefore proposed (D-394).
- **Pause.** `SIGSTOP`/`SIGCONT` is rejected:
  - live HTTP calls and the per-cell timeout run on wall time;
  - the T1 watchdog's interval maths (G.4.12) assumes the process runs;
  - Windows has no equivalent.

  "Pause" is a **drain**: finish in-flight units, flush, exit resumably (D-394).
- **Identity across restarts.** pid plus `psutil.Process.create_time()`, so that pid reuse cannot cause a mis-attach.

### Q2.3 A machine-readable progress channel: compared with logs and corpus files

**What exists:**
- `--progress-file PATH` already writes `agentprov-progress/0.1` JSON lines through the D-8 sink:
  - non-blocking: `put_nowait` on a 4,096-item queue that drops and counts when full;
  - a daemon writer thread that flushes per line.
- It can therefore be tailed live (`cli/feedback.py`, `progress.py`). Event kinds: `start`, `unit_start`, `unit_done`,
  `step`, `trace`, `end`.

**Gaps found** (CLI inventory §5.3):
1. `import` emits only `start` and per-execution `unit_done`: no `unit_start` and no per-stage `step`. Container
   sources mix container totals with sample `unit_done`s, so the percentage can exceed 100 %.
2. The T1 pool's per-job reporter `_report_job` (`io/workers.py:1440`) is never reached, because no caller passes
   `progress` to `pool.run`.
3. `package` and `verify` emit nothing (verify passes the sink only to rederive).
4. The file is opened with `"w"`, so a resumed job truncates its own history.
5. There is no periodic snapshot. A reader that joins late, or that misses lines dropped by the D-8 queue, cannot
   recover the counters.
6. Live `step`s carry `req` but not the session id, so a preview cannot find the capture log from progress alone.
7. `--progress-file` is ignored by `info`, `fetch`, `backends`, `purge` and `inspect`. Only `fetch` and `backends build`
   matter for a GUI; their dashboards fall back to "running / ended".

**Alternatives:**

| Channel | Live during `import`? | Counters | Cost | Notes |
|---|---|---|---|---|
| Parse the log (`--log-file`, JSON) | yes | prose plus fields; stage counters not derivable at INFO | DEBUG adds I/O per record | good for the Logs pane, wrong for dashboards |
| `executions.jsonl`, `register.jsonl`, `corpus.json` | **no**: import rewrites them only at flush, at the end or on interrupt (`importer.py:1985-1988`); derive per batch of 256; run per attempt | complete but late | re-reading 15–53 MB files per poll | used after a job ends |
| Accounting | not a file: it is the verdict in the AER seal, copied into `live.sessions[].accounting` | — | — | post hoc only |
| **`--progress-file` (extended)** | yes | complete with the additions below | ~1 µs per event in the producer (§M1) | **recommended** |
| A socket or pipe protocol | yes | yes | low | rejected: a server, and re-attach breaks |

**Proposal (D-393, a core change).** `agentprov-progress/0.2`, additive:
- `run` header;
- per-file `seq`;
- `stage` begin and end;
- `heartbeat`: an absolute snapshot every 2 s with per-stage done/total/failed/running, counts, the top issue codes,
  worker pids and busy count, queue and dropped. This follows Docker's absolute `current/total` pattern, so readers can
  recover from gaps [S20];
- `worker` spawn and exit;
- `session` (live, with the staging path);
- `control` acknowledgement;
- `end.outcome`;
- `--progress-file` appends and rotates at 8 MiB (one `.1`);
- the pool reporter is wired up, and `package` and `verify` gain stage events.

Schema and reader algorithm: design §5.

**Overhead.**
- Measured in §M1: one `queue.Queue.put_nowait` ~1.0 µs including the drop path; JSON encode, write and flush in the
  writer thread ~13.5 µs per line.
- An fsync per line would be 40–60 µs on this Mac's SSD and is not proposed. Durability is not needed for progress,
  because the summary and the corpus documents are authoritative.
- At `status` level a 38,281-execution import adds ~38k lines (≈ 0.5 s of writer-thread time) plus one heartbeat every
  2 s, which is under 0.01 % of a multi-hour run.
- It is byte-neutral for corpora: progress is outside every stage function and `fn_digest`.

The CLI owns the counters; the GUI computes rates and ETAs (design §5.4).

### Q2.4 Development-session status (workflow tools, merged from main `4b343df5`)

- `tools/session_status.py` (D-428) writes one `agentprov-session-status/1` file per parallel session, atomically and
  under an `flock`, with git facts computed on every write.
- `tools/queue_status.py --json` aggregates them with the suite queue and flags stalls. It writes nothing and passes
  every string through `safe_text`.

These describe development sessions, not CLI jobs. The GUI shows them read-only in a Sessions sub-tab of Runs (design
§6.2a), through `queue_status.py --json` as a subprocess, so that the stall rules exist in one place.

## Q3. Progress display and log pane

### Q3.1 The most informative live display for a full corpus run or the regeneration round

**Per job:**
- the argv;
- mode (release or dev);
- a **stage strip** with done/total/failed/running per stage. Stage names come from the code: for import, store,
  expand, map, seal, SEM, PROV, validate and index; for recompute, expand, aer, sem, prov, validation and views;
- throughput as a bias-corrected EWMA (tqdm's estimator, α = 0.3) next to the overall mean [S21];
- ETA **as a range**, from the long-window and short-window rates. There is no primary standard for ETA confidence, so
  this is a heuristic; it is suppressed until 30 units **and** 60 s have passed;
- counts: sealed, with issues, degenerate, failed, excluded, duplicates, withheld, skipped on resume;
- **failures by code**, linked to the Logs filter;
- worker utilisation (busy out of configured, plus per-process CPU and RSS when the System tab is on);
- the **resume point** ("resumed: n units skipped");
- dropped events (the D-8 queue).

**For `run`:**
- cells planned, done before, attempted, conclusive, inconsistent, inconclusive, failed and quarantined;
- canary status;
- per-slot in-flight cells with their age.

**For the regeneration round:** a corpus × stage matrix of done/total pills, one row per batch step.

Ninja (`%f/%t`, rates `%o`/`%c`, ETA `%E`) and rsync `--info=progress2` (whole-transfer statistics) are the closest
precedents for a combined overall-plus-current display [S21].

### Q3.2 Log pane

- **Source:** the CLI's `--log-file` (DEBUG, JSON lines, append mode, redacted) or `stderr.txt`.
- **View:** a `QListView` over a fixed-capacity **ring-buffer model** with `uniformItemSizes`. Qt documents that
  `uniformItemSizes` "enables the view to do some optimizations" [S8].
  - This is preferred to `QPlainTextEdit.setMaximumBlockCount`. That option is documented as efficient for logs [S8],
    but it lays out text and cannot filter per field.
  - Forum reports of `QPlainTextEdit` slowdowns are Qt 4-era and unverified.
- **Filtering:** level, logger, stage, code, ex, and substring or regex search.
- **Follow and pause:** pause stops auto-scroll while ingestion continues. Evictions during a pause are counted and
  shown.
- **Copy:** plain text, already escaped.
- **Back-pressure:** at most 1 MiB is read per 250 ms tick, rows are inserted once per tick, and a "lagging" indicator
  shows when the reader falls behind. The ring caps memory (50k × ~300 B ≈ 15 MB); the file on disk keeps everything.
- **Tailing:** file-change notifications are only **hints**:
  - inotify coalesces and can overflow;
  - ReadDirectoryChangesW reports size changes late, after cache flushes;
  - FSEvents coalesces;
  - `QFileSystemWatcher` documents that "some of the changes might not emit this signal" [S22].

  The robust pattern is `tail -f`'s: keep the file open and read from the saved offset on a timer (250 ms) as well as
  on hints. Split on `\n`, keep the partial last line, and detect rotation or truncation by identity or size [S22].

## Q4. System monitor tab

- **Name: "System".** "Activity" collides with `prov:Activity`, the core PROV term the Viewer shows everywhere.
  "Runs" already names the job list.
- **Content:**
  - CPU per core;
  - memory and swap;
  - per-job process tree (T0, T1 workers, the T2 backend worker, `dot`) with RSS, CPU %, threads and open files;
  - system disk I/O;
  - free disk under `AGENTPROV_HOME`;
  - temperature where available.
- **Platform facts (psutil 7.2.2 [S13]):**
  - `sensors_temperatures()` exists only on Linux and FreeBSD; it returned nothing here on macOS (§M4).
  - `Process.io_counters()` is not on macOS (§M4: `AttributeError`).
  - `open_files()` on Windows is "not guaranteed to enumerate all file handles".
  - The first `cpu_percent()` returns a meaningless 0.0.
  - `oneshot()` speeds up multi-attribute reads by 1.6–2.7×.
- **Measured per-call costs** (§M4; macOS, 13-process tree):

  | Call | Cost |
  |---|---|
  | `cpu_percent(percpu=True)` | 0.027 ms |
  | `virtual_memory()` | 0.003 ms |
  | `disk_io_counters()` | 0.19 ms |
  | per-process `memory_info + cpu_times + num_threads` over the tree | 0.20 ms |
  | `num_fds` | 0.30 ms |
  | `open_files` | 0.19 ms |
  | **`children(recursive=True)`** | **37 ms** (it walks every pid on the system) |

- **Budget and isolation:**
  - The sampler runs in a `QThread` of the **GUI** process at 1 Hz, and only while the tab, or the dashboard's worker
    panel, is visible. Nothing is ever injected into job processes.
  - The process set comes from the `worker` progress events (D-393). Without them, the tree walk is refreshed every
    10 s.
  - Measured (§M2): the naïve sampler, walking the tree every second, cost ~20 ms per sample. With the 10 s refresh it
    dropped to 2.3–3.8 ms per sample (~0.25–0.4 % of one core), and with known pids it falls to ~0.3–0.5 ms.
  - Against a 12-worker CPU-bound job, the observer's CPU was ≈ 0.1 % of the job's CPU time. Wall-time differences were
    inside the ±25 % noise of the shared machine, so the measured slowdown is "not detectable", and the CPU share is the
    bound reported.

## Q5. PROV visualisation

### Q5.1 What the W3C documents define, and whether `render/style.py` follows it

- **No normative graphical notation exists.**
  - PROV-DM: "All figures (including UML diagrams) are informative"; §4.1 gives the shapes ("oval, rectangular, and
    pentagonal") and says the illustrations "should not be seen as an alternate notation" [S14].
  - PROV-O: "All figures and diagrams are informative"; captions describe "Entities as yellow ovals, Activities as blue
    rectangles, and Agents as orange pentagons" [S15].
  - PROV-PRIMER: "The arrows point from the future to the past" [S16].
  - **The hex colours** #FFFC87 (entity), #9FB1FC (activity) and #FED37F (agent), with strokes #808080 and blue, are
    stated on the Provenance WG wiki page "Diagrams" (archived 2012, unattributed) [S17], not in any Recommendation or
    Note. The page itself says agents are "octagonal" in one place and "pentagon houses" in another; PROV-DM says
    "pentagonal".
- **`prov` 3.2.2 `prov/dot.py`** [S18]:
  - `DOT_PROV_STYLE` uses exactly the wiki colours:
    - entity: oval #FFFC87, border #808080;
    - activity: box #9FB1FC, border #0000FF;
    - agent: house #FED37F, no border colour;
    - bundle: folder `aliceblue`.

### Q5.2 Interactive graph view

- **Layout source.** Graphviz `-Tjson` is xdot information in JSON: `bb`, node `pos`/`width`/`height`, edge spline
  control points and `_draw_` ops. `-Tjson0` gives the same without draw ops, and `-Tplain` is minimal and in inches
  [S19]. The GUI parses node positions and edge splines and **ignores text draw ops**: labels are drawn from the model
  through `QGraphicsSimpleTextItem`, which never interprets markup (§M8). Graphviz's y axis points up and Qt's down.
- **Process controls:** the G.8.6 `render` controls are reused (fixed argv, stdin, minimal environment, empty cwd, new
  session, 120 s timeout, output cap). D-397 proposes adding `json` to `render.dot.run_dot`'s format allowlist so the
  controls stay in one place.
- **Drawing:** built-in C++ items (`QGraphicsEllipseItem`, `QGraphicsRectItem`, polygon, `QGraphicsPathItem`). No Python
  `paint()` overrides, which would be the bottleneck in PySide6 (engineering judgement). Items sit in a **static BSP
  index** with an explicit `sceneRect` [S8].
- **Interaction:** pan with left-drag; zoom with the wheel; +/−, 100 % and Fit buttons; hover **popover** (a frameless
  widget with a plain-text attribute table, not a `QToolTip`, because tooltips are rich text); bundle toggles; evidence
  class by line style with a filter; search and k-hop focus. Details in design §7.2.
- **Scale:**
  - Locally, the largest real document (agentdyn) has ~2,794 elements and ~4,224 relation statements across all bundles
    (`render.graph` draws 2,766 nodes and 8,465 edges, counting each target and claim link). The core bundle
    is ≤ ~700 nodes. Assessment mentions make up ~2.3k of the 2.8k nodes, which motivates the "collapse mentions"
    default.
  - Measured on synthetic PROV-shaped scenes (§M6, offscreen raster):

    | Nodes | Build | Fit, labels | Fit, LOD, no AA | Zoomed viewport | RSS |
    |---|---|---|---|---|---|
    | 3k | 0.30 s | 182 ms | 43 ms | 32 ms | 158 MiB |
    | 10k | 0.49 s | 635 ms | 162 ms | 67 ms | 347 MiB |
    | 50k | 2.3 s | 2.0 s | 1.37 s | 260 ms | 1.7 GiB |

  - So 10k nodes is interactive when zoomed in, but not at fit-to-view without an overview raster, and 50k is too heavy
    for one-item-per-element.
  - The design uses:
    - LOD tiers (the Qt 40000 Chips pattern [S23]);
    - an **overview raster** for zoomed-out views: one `QImage` rendered in a worker thread; Cytoscape.js's
      `textureOnViewport` is the same idea [S24];
    - label hiding at LOD transitions;
    - collapsing (mentions, passes, inference as overlays);
    - Cytoscape desktop's precedent: labels only below 200 visible nodes and coarse rendering above 4,000 [S24].
  - The BSP index matters: 10k nodes with `NoIndex` needed 2× the build time and 2× the zoomed paint (§M6).
  - Moreau's provenance-type aggregation [S25] is a principled, deterministic summary for future "summary views"; it is
    not in v0.1.
- **Layout time** (§M7, §M7b, §M12; child CPU time, so load does not inflate it):
  - **Core bundles:** 0.08–0.12 s with `dot` on every sampled real document, including the largest (221 nodes).
  - **"All" bundles:** inference edges multiply the edge count (for example 70 → 261 nodes and 18 → 667 edges), and
    `dot` time grows sharply:

    | All-bundle document | With edge labels | Without labels | Fast flags |
    |---|---|---|---|
    | 261 nodes / 667 edges | 11.9 s | 2.7 s | 0.9 s |
    | 544 nodes / 1,714 edges | > 320 s (killed) | 58.6 s | 10.0 s |
    | largest, 2,766 nodes / 8,465 edges | > 740 s (killed) | > 480 s (killed) | 121 s |

  - **Synthetic layered DAGs:** default `dot` exceeded 300 s of CPU from 1k nodes up. With the fast flags it took 4.5 s
    at 1k and 72.7 s at 3k, and at 10k it was killed after 644 s of CPU. `sfdp` took 0.24 s, 0.68 s, 3.05 s and
    10.97 s for 300, 1k, 3k and 10k nodes.
  - **A pure-Python layered layout** (cycle-breaking, longest-path ranks, 4 barycentre sweeps; §M12) took **10 ms** for
    the largest real all-bundle document, 37 ms at 10k nodes and 0.24 s at 50k. Its drawings are of lower quality than
    `dot` (no spline routing, simpler crossing reduction), but it preserves time direction.
  - **Hence:**
    - `dot` for the core and small graphs (the quality layout, cached by digest);
    - inference and assessment drawn as overlays on the core layout (edges between placed nodes; mention badges);
    - the GUI layered layout for full or large layouts;
    - `sfdp` only as an optional "organic" view;
    - edge labels never sent to `dot`.
  - `agentprov render --bundle all` on large documents will hit the same `dot` cost and its 120 s timeout (§R).
- **Incremental layout** (DynaDAG, North and Woodhull 2001 [S19]) is not available in `dot`. Only the live preview needs
  it, and it uses an append-only layered placement (Q6).

### Q5.3 PROV-JSON, AER and SEM views

- **PROV-JSON:** a collapsible tree (document → prefix, top level, bundles → sections → statements → attributes) built
  from the strictly loaded document dict and `render.graph`'s model (statement keys; the GUI does not import the private
  `validate._provdoc`), plus a read-only raw-text pane. Selection is synced with the
  graph by statement key.
- **AER:** records grouped by the 13 kinds, with envelope fields (`ev`, `by`, `evf`, `rule`, `src` locators, `unk`
  reasons, `after` edges). The links go from records to PROV through `apv:sourcePointer` and to SEM annotations by
  target. Content fields (message parts, tool args and results, fixture content, blobs) stay hidden until "Show
  content", and then go through `quote_untrusted(text, locator)`.
- **SEM:** annotations by target, with type, value, `ev`, rules, premises and method/confidence.
- **Raw:** locators resolved by `aer.locators.LocatorResolver` to digest-checked bytes, shown only fenced and truncated.
  Artefact media are never rendered (T-10).

## Q6. Experimental live PROV view

- **Feasibility.** Yes, as a separate-process **preview**:
  - The capture writer (`capture/src/agentprov_capture/log.py`) opens `O_WRONLY | O_CREAT | O_APPEND` and writes each
    event as one JCS line with a single `os.write` loop. It has no Python buffering, fsyncs only `pass.end` and
    `session.end`, and refuses symlinks. Each line's `prev` is the sha256 of the previous line.
  - A tailer that consumes only LF-terminated lines, keeps the fragment and re-checks `prev` is exactly what
    `verify.split_lines` and `verify_chain` already do (`torn_tail`, `unsealed`).
  - Blobs are renamed into place before the event that cites them.
- **Discovery.** Logs live at `$AGENTPROV_HOME/staging/<session>/raw/capture/<session>.capture.jsonl`, up to `--jobs` at
  once, and the directory is deleted after ingest unless `--keep-staging` is set. Progress steps carry `req` but not the
  session id, so the proposed `session` progress event (D-393) is the discovery mechanism.
- **Limits:**
  - **Messages appear only at `pass.end`**, as one blob, so a preview cannot show message entities mid-pass. It shows
    activities (pass, model invocation, tool execution, decision) as their events arrive.
  - Staged files have passed only the worker's redactor, not T0's literal secret scan (`cli/live/staging.py`), so the
    preview reads **envelope metadata and ids only**, never `data` content or blobs.
- **Invariant 1.** Corpus PROV comes from the engine's versioned rule catalogue after recording. The preview's mapping
  (design §9) is a display heuristic. It is never saved and never compared, and every view carries a "Preview: not
  corpus provenance" banner.
- **Overhead (§M10):**
  - POSIX readers take no locks that could block `os.write`.
  - On Windows, CPython's `open()` shares read and write (no delete) by default, so the reader is compatible with the
    writer's handle. This rests on a secondary source citing CPython issues [S22].
  - Measured with 8 synthetic writers at 50 events/s each (far above a real live run, where a model call takes seconds),
    with and without a tailer that polls every 250 ms and re-checks the chain:
    - the writers' `os.write` latency is unchanged within noise (p50 50–62 µs either way; the tails are dominated by
      fsync);
    - the tailer costs ≈ 0.8 % of one core including its start (≈ 0.55 % steady).
  - The tailer runs as a separate process at below-normal priority, so on a 12-core machine its effect on the capture's
    `ts` and `mono_ns` is within measurement noise.
- **Recommendation:** off by default; a separate helper process; ≤ 1 Hz redraw; append-only layered placement; ids only
  (D-398).

## Q8. Live generation settings

- **Keys today:**
  - `run` reads keys **only** from a dotenv file: `--env-file`, or else `<repo root>/.env`, through `dotenv_values`
    (`run.py:414-428`).
  - It takes only the selected endpoint's names from `endpoints.toml`:
    - `DEEPSEEK_API_KEY`, `OPENAI_API_KEY`, `OPENROUTER_API_KEY`;
    - `*_BASE_URL`;
    - `*_MODEL`;
    - `REASONING_EFFORT`.
  - It passes only the key variable into the T2 worker environment, from the fixed allowlist (`PATH=/usr/bin:/bin`,
    private `HOME`, `LANG`, `TZ`), and registers the value for redaction.
  - It needs the `live` extra (python-dotenv).
  - A GUI cannot hand keys over by environment variable, and writing a temporary `.env` would put a key on disk in
    plain text.
- **Proposal (D-395):**
  - `run --env-stdin` reads one strict JSON object (≤ 64 KiB, the same name allowlist) from stdin before any other
    step. It is mutually exclusive with `--env-file` and **disables the default `.env` read**.
  - The GUI stores keys with `keyring` [S26]:
    - Allowed back-ends: macOS Keychain, Windows Credential Locker, Secret Service, KWallet.
    - **Refused:** `keyrings.alt` plaintext (priority 0.5) and encrypted (0.6), `fail`, `null`, and chainers containing
      them. Those can be selected silently when installed, so the back-end is checked after loading, because
      `keyringrc.cfg` and `PYTHON_KEYRING_BACKEND` can redirect it.
  - Headless Linux without D-Bus Secret Service gets "no keys from the GUI".
  - keyring's macOS caveat: "any Python script or application can access secrets created by keyring from that same
    Python executable". This argues for a bundled app with its own executable identity in release builds.
  - QtKeychain is C++ only, with no official Python binding (*unverified*).
- **Consent and cost.**
  - `_consent` prints the cell count, endpoint, model and key variable, and needs a TTY or `--i-consent-to-api-costs`.
  - **The preflight probe (one paid call) runs before consent** (`run.py:1044-1047`). The GUI's confirmation therefore
    covers the probe, and "Preflight only" is a separate R2 action.
  - The CLI has **no cost estimator** (no price table; `grep cost|estimat` finds only the consent text). The estimate is
    the GUI's (design §8.3):
    - cells from `run --dry-run --json`;
    - calls and tokens per cell from earlier executions in opened corpora (index facet `n.model_calls`, AER
      `model_call.usage`);
    - prices from the user's dated table, with nothing shipped;
    - p50 and p90 ranges.
- **Model choice per backend:**
  - shorthands deepseek, openai, openrouter, gemini, llama, qwen, glm, ollama, omlx;
  - or `--endpoint` plus `--model-id`;
  - or `--llm-script` (scripted, test_only, no keys, network blocked);
  - plus temperature, reasoning effort, LLM element (`gateway_compat` exits 5 on AutoDojo) and text tool calls.
- **Suites, attacks, defences:**
  - `--suite`, `--user-tasks`, `--injection-tasks`, `--attack` (`autodojo` alone, with cache and variant), `--benign`;
  - `--defence` other than `none` exits 5;
  - or `--plan PLAN.toml` (`agentprov-run-plan/0.1`).
- **`--m5ultra` and `--tune-jobs`:**
  - `--m5ultra` is shorthand for `--preset m5ultra` and is **dry-run only**. It computes `jobs` as the minimum of the
    compute cap (8 up to 15B active parameters, 6 up to 40B), the memory cap and the server cap (default 8), and a
    stagger of 1 s per worker. A live run with a preset exits 5.
  - **`run --tune-jobs` does not exist** (spec N.2.1a(4) only).
  - The GUI's "Tune" runs the preset dry run and applies the resulting `--jobs`/`--start-stagger` to the real run.
- **Gating today:** the registry shows `agentdojo · live` and `autodojo · live` as `planned`, so real-model runs exit 5.
  The whole flow can be built and tested with scripted runs before promotion (design §8.1).

## Q10. Packaging and release flow

- **Seal** (`package --corpus DIR --corpus-version X.Y.Z`).
  - Preconditions, each refusing with exit 4: stages complete; strict validation; no `interpreter_advisory`; pins
    verified with no `local` origin; licence policy; licence files; a clean known git commit; a closed-world tree; card
    lint.
  - Steps: write `rules/`, `schemas/`, `LICENSES/`, `CHANGELOG.md`, `DATASHEET.md` and the sealed `corpus.json`; withhold
    (sidecar `DIR.withheld/`, 0700); `checksums.sha256`; `verify --level chain`; swap `.partial` to `DIR`.
  - The output is a `SealReport` (content and root digests, counters).
- **Withholding** (D-230..D-237):
  - `WITHHELD.json` holds entries with reason (secret, personal_data, licence, takedown) and basis (purge, raw_policy,
    profile_rule, container), affected executions, and policy rule ids only. No value, fragment or source key.
  - Profile `[withhold]` scans run in 1 MiB chunks at sealing, with backstops in `chain` and in the deposit builder.
  - The CLI prints counts only. The GUI shows the same: counts and rule ids, never values, and never opens the sidecar.
- **Deposit** (`package --deposit OUT --corpus … --metadata release.toml --release-date`). It is offline by construction
  (an AST and fresh-interpreter test), and it refuses:
  - below CPython 3.14.8;
  - an advisory;
  - an unsealed corpus;
  - non-strict validation;
  - a test_only corpus;
  - an all-withhold corpus;
  - mixed licence classes;
  - a `views/` tree;
  - an untriaged `<corpus>.release-scan.json`;
  - a withhold-backstop hit.

  It produces deterministic split zips, `DEPOSIT-MANIFEST.json` (sha256 and md5 per archive), `deposit-metadata.json`,
  README, CHANGELOG and DATASHEET. `verify` reads deposits in archive mode (no extraction).
- **GUI flow:** design §6.7.
  - It calls only `package` and `verify` and never re-implements them.
  - Step 7 checks that the release scan exists and is triaged; running `tools/release_scan.py` stays a terminal step.
  - It ends with "Nothing has been uploaded" and a manual-upload checklist.
  - It is ready for the first Zenodo release once a sealed, scanned corpus exists. Locally **none of the 25 corpora under
    `~/.agentprov/corpora` is sealed**; 4 trial corpora under `migration-work` are, e.g. `phase10k/trial/c2seal` with
    `WITHHELD.json`, a good GUI test target on a copy.

## R. Risks and open points

1. Core changes D-393, D-394, D-395 and D-397 need an owner session. The GUI phases G1 and G2 run without them, with
   degraded progress.
2. No free-threaded PySide6. Irrelevant to the core.
3. Nuitka's licence for compiled output is unverified, so pyside6-deploy is not used until it is read.
4. LGPL compliance for bundles: one-folder layout, notices and a source offer. Legal judgement stays with the user.
5. keyring's macOS caveat (any script run by the same Python executable can read the item) argues for signed bundles
   with their own identity, or for keeping real-model runs on the CLI until bundles exist.
6. `migrate` writes reports into the repository's `migration/` by default, a directory that is neither tracked nor
   ignored (CLI inventory). This is outside the GUI's scope, and is noted for the orchestrator.
7. Graphviz "all"-bundle layouts of the largest documents with edge labels exceed the 120 s G.8.6 timeout. The GUI
   avoids edge labels in layout, and `agentprov render --bundle all` may hit the same limit (orchestrator note).
