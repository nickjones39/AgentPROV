# D-43: live corpora cannot be re-mapped (`recompute --stages aer` exits 5); their SEM/PROV/validation re-derive (phase 11, U2)

Status: implemented on branch `phase-11-u2` (U2); for consolidation into DECISIONS.md.
Code: `resolve_plan` in `src/agentprov/corpus/derive.py` (`DeriveUnsupportedError`, code `corpus.derive.live_remap`).
Test: `test_a_live_corpus_cannot_be_remapped_but_can_be_rederived`.

## Decision

For a corpus whose manifest has `"mode": "live"`, `recompute` with `expand` or `aer` among its `--stages` is refused
with exit 5 (unsupported) before anything is read beyond the manifest and index, with a message that names the
alternative. Without `--stages`, `recompute` of a live corpus starts from the stored AERs (the layers above the AER and
the views/compat it has), not from raw. `recompute --stages sem,prov,validation` (and `views`,
`compat`) works exactly as for an import corpus: the stored AER is copied, its seal re-verified, and the layers above it
are re-derived and compared. `derive` (which never re-maps) adds layers to live corpora as to any other.

## Why

A live AER is mapped from capture logs by the live session pipeline (`adapters/runner/session.py`), not by
`import_source`; its raw objects are capture logs whose mapping depends on the capture session and the backend
identity, and the import path has no tree for them. Re-mapping would need a second, live-specific re-map path that
phase 11 does not own (`adapters/` is read-only here). The layers above the AER are a pure function of the AER and
are handled by the same `prov` job as for imports, so they need no special case.

## Rejected alternatives

- **Re-mapping capture logs through `import_source`**: wrong pipeline (attempt indices, session identity, capture
  verification); it would silently produce different AERs.
- **Exit 2 (usage)**: the request is well-formed; the capability is missing, which is exit 5 (N.1.3).
- **Silently skipping the AER stage**: a recompute must do what it is asked or refuse.
