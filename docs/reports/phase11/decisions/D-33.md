# D-33: snapshot reconciliation, the sealed snapshot origin from the recorded pin, `subtree` / `subtrees` (phase 11, U3)

Status: implemented on branch `phase-11-u3` (U3), for consolidation into DECISIONS.md by the orchestrator.
Code: `src/agentprov/corpus/manifest.py` (`snapshot_counts`, `corpus_counts`, `is_exclusion`, `snapshot_origin_from_pin`),
`src/agentprov/corpus/spec.py` (`check_origin`), `src/agentprov/corpus/package.py`. Tests:
`tests/unit/corpus/test_manifest_builders.py`, `tests/unit/corpus/test_package.py`, `tests/unit/corpus/test_spec.py`.

## Decision

1. **Counts are recomputed, never copied.** The sealed manifest's snapshot and corpus counts (H.2.3, H.2.9) are computed
   at sealing from `executions.jsonl`, `register.jsonl` and `raw/members.jsonl`. The importer's counters in the working
   manifest are not read.
2. **A candidate is a selected execution-bearing file or member.** For a snapshot `s`:
   - `executions` = the index rows whose `snapshot_ids` contain `s` (one execution with several origins counts once);
   - a **selection exclusion** is a `select`-stage `not_imported` register entry with a `{snapshot_id: s, path}` subject
     whose path an exclude glob of `s`'s effective selection matches *with the entry's own code* (the families' glob
     matcher, `**/` matching zero directories). Exclusions are counted in `selection_excluded` by code and are never
     candidates (H.6.1 R1);
   - `not_imported` = every other `not_imported` entry attributed to `s` (a `{snapshot_id, path}` subject; an `{ex}`
     subject through the row's single snapshot; a `{source_key}` subject only in a single-snapshot corpus, otherwise the
     seal refuses: the reconciliation would be unverifiable);
   - `candidates` = `executions + not_imported`.

   This fixes the working manifests by definition: agentharm-p10 records `candidates: 6` (the six `.eval` containers)
   against `executions: 1056`; sealed, its snapshot has `candidates 1056 = 1056 + 0` (the 1,056 selected sample members
   that bear executions; the six `header.json` members are selected but are supporting artefacts, not candidates).
   ROPE's working manifest counts its 14,066 exclusions as `not_imported`; sealed, they are `selection_excluded`
   (`select.owned_elsewhere` 13,765, `select.not_execution_artefact` 301) and `candidates = 10,791 + 0`. AgentDyn A:
   949 exclusions, 9,442 `select.dialect_planned` candidates (variants B and C) not imported, `candidates 47,723`.
3. **The sealed snapshot origin comes from the recorded pin, never `local`.** `--input` imports record a `local`
   snapshot origin plus the `pin` that vouched for each file. Sealing builds the snapshot origin from that pin and the
   object-level origins of the snapshot's primary objects (and, for archive members, their containers):
   - `git` objects: `{kind: git, repo, commit, subtree[, subtree_sha1]}`; `repo` is the pin's, else the single
     repository of the objects at the pinned commit; `subtree` is the pin's tree without a trailing `/` (`""` for the
     whole commit, e.g. ROPE, Mandate); `subtree_sha1` when the pin records the tree id;
   - `corpus` objects (the AgentDojo-PROV release, R-26): `{kind: corpus, corpus, version, producer_commit}`, whose
     producer commit must equal the pin's commit.

   Sealing refuses (exit 4) when no pin was recorded, when `verification.unverified > 0`, when any object origin is
   `local`, when object origins disagree with the pin (commit, repository, mixed kinds), and when the spec's origin
   differs from the one the pin gives.
4. **`subtree` string / `subtrees` array.** A git snapshot origin has exactly one of `subtree` (a string; one tree or
   `""`) and `subtrees` (a sorted array of two or more non-empty relative paths, for a selection that spans several
   trees; `subtree_sha1` goes only with `subtree`). No v0.1 corpus uses `subtrees`; the spec parser and the schema
   accept it so that a multi-tree snapshot needs no format change.

## Why

H.2.3 requires `candidates == executions + not_imported` and the release refuses `local` origins; the working manifests
break both (agentharm, ROPE; every `--input` import). Defining the counts from the register makes them recomputable by
`verify --level chain` (U4) from the corpus alone, and taking the origin from the pin keeps the provenance claim at the
strength the import verified it (blob or listing check).

## Rejected

- Copying the importer counters (they count containers, and count exclusions as `not_imported`).
- Counting containers as candidates for archive sources (an execution-bearing member is the unit the importer maps).
- Recording the local path or a placeholder origin in a sealed manifest (development only; invariant 2).
- Telling exclusions apart by the register `detail` text (generated prose, not data).
