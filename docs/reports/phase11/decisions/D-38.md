# D-38: deposit verification input and archive mode (no extraction; per-member label, size, CRC-32 and sha256) (phase 11, U4)

Status: implemented on branch `phase-11-u4` (U4), for consolidation into DECISIONS.md by the orchestrator.
Code: `src/agentprov/corpus/archive.py` (archive-backed source and reader), `src/agentprov/release/verify.py` (deposit and
lone-meta checks), `src/agentprov/corpus/verify.py` (the levels, shared by tree and archive mode),
`src/agentprov/cli/verify.py`. Tests: `tests/corpus/test_deposit_verify.py`, `tests/corpus/test_tamper.py`,
`tests/corpus/test_verify.py`. Rehearsal: `docs/reports/phase11/verify-rehearsal.md`.

## Decision

1. **Inputs.** `agentprov verify --corpus PATH` decides the mode from `PATH` without following a link: a directory that
   holds `DEPOSIT-MANIFEST.json` is a **deposit** (archive mode); a regular file `<corpus_id>-v<version>.meta.zip` is a
   **lone meta archive** (archive mode); anything else is a corpus tree (N.1.5 resolution, tree mode). A single data
   archive (`.aer.001.zip` alone) is not an input: without the meta archive there is no `checksums.sha256` to check it
   against.
2. **No extraction, the G.3.5 gate.** Every archive is opened through `agentprov.ingest.archives` (read-only use): the
   EOCD size pre-check before `zipfile`, warnings as errors (duplicate names, overlaps), member count, prefix (polyglot)
   and overlap checks, and the per-member gate (links, encryption, method, name, collision, size, ratio). Members are
   streamed with `ZipFile.open` (declared-size stop, CRC check) in 1 MiB chunks and hashed in memory; nothing is
   written to the filesystem. A whole-archive rejection is a finding named after the archive; a member-level rejection
   is a finding named `<archive>#<index>` (the raw name is data and is never echoed).
3. **Labels.** A member name is a label: it must start with the corpus prefix `<corpus_id>-v<version>/` (D-42 item 9;
   `archive.member.prefix`), and the rest must be a file of the H.1.2 grammar (`archive.member.path`). A label present in
   two archives is a finding (`archive.member.duplicate`) and neither copy is trusted.
4. **Closed world over the union.** For each corpus of a deposit, the union of its archives' members is the closed
   world of its own `checksums.sha256` (read from the meta archive): every listed file present and matching
   (`checksums.missing`, `checksums.mismatch`, `checksums.unreadable` with the gate's code), nothing unlisted
   (`checksums.unlisted`). This is the archive-mode `ChecksumSource` (`corpus.archive.ArchiveSource`), the extension
   point U1 left in `corpus.integrity`.
5. **Deposit checks** (`deposit.*`): the deposit manifest is strict JSON of `agentprov-deposit-manifest/0.1` whose
   archive and document names are plain file names; the deposit directory holds exactly the listed archives and
   documents and the manifest, regular files only (`deposit.unlisted`, `deposit.missing`); each archive's and document's
   size, sha256 and md5 equal the manifest's; per archive, `n_members`, `uncompressed_bytes` and `members_sha256`
   (sha256 of the sha256sum-format listing `<hex>  <member name>\n`, sorted, D-42 item 10) recompute from the members
   and every member lies in the archive's stage; per corpus, the root digest (sha256 of the archived
   `checksums.sha256`) and the content digest equal the manifest's, and `coverage.files` equals the tree's file count.
6. **Levels in archive mode.** The default level is `chain`, run unchanged over an archive-backed `CorpusReader`
   (`corpus.archive.ArchiveCorpusReader`): manifest, digests, index, register and counts, AER seals, raw objects and the
   member CRC-32s, SEM/PROV inputs, facets, catalogue authority (HL-T9: "reads the deposit without extraction and passes
   chain"). `checksums` is available. `rederive` exits 5 (`verify.archive.unsupported`): re-deriving needs a raw store
   on disk and no AgentPROV command extracts a deposit (H.10.3(1)); re-derive a sealed tree instead.
7. **Lone meta archive.** Its members are checked against its own `checksums.sha256`; the manifest is validated; the
   checks that need a file of the other archives (listed files not present, executions, raw objects) are reported
   `unverified` with code `archive.not_present`, never passed, as are the manifest members that need every AER
   (`records_by_kind`, `generic_types`, `models`, `framework_identities`, `rules_used`). Dev mode exits 0 with the
   unverified findings listed; `--release` fails on them (exit 1) and needs `--root-digest` (D-39), because no deposit
   manifest anchors the root digest.
8. **Where it runs: in the CLI process, not in a T1 worker.** G.3.5 and H.5.5 place archive reading in T1. A T1 job kind
   for it would be a new kind in `io/workers.py`/`worker.py`, which belong to phase 12 (PLAN ownership rules), so
   `verify` reads the archives in-process with the same ingest gate. Bounds: the pre-check bounds what `zipfile`
   allocates for the central directory; members are streamed, never held whole; archive-mode limits
   (`corpus.archive.ARCHIVE_LIMITS`) are the G.3.2 defaults with `max_member_bytes` raised to the deposit format's own
   member bound (2^31 - 1 bytes / 1.05, the builder's no-ZIP64 limit; the default 256 MiB would refuse a legitimate raw
   object) and `max_total_bytes` raised to 64 GiB per archive (streaming, so it bounds CPU, not memory; the per-member
   ratio cap of 200 still holds). Moving archive reading into a T1 `verify` job kind is a phase-12 follow-up.
9. **Interpreter guard.** Release mode below CPython 3.14.8 is refused before any archive is opened (exit 3; AD-16,
   G.3.8); dev mode reads with the advisory and says so.
10. **Deposit builder.** `agentprov package --deposit` injects `verify --level chain` in release mode
    (`cli.deposit.verify_chain`, `build_deposit(verify=...)`; H.10.1(3)), so the deposit manifest records
    `verification.level = "chain"`.

## Related implementation notes (U4; no decision number of their own)

- **`seal()` runs `verify --level chain`** (N.2.11 step 3) over the sealed tree before the swap, in release mode (an
  unverified or tombstoned finding blocks sealing too); a failure is `corpus.manifest.verify` (exit 1).
- **Chain recomputes the manifest.** Every member sealing computes from the corpus (`files`, `digests`, `counts` and
  each snapshot's counts, `duplicates`, `validation` incl. `linkage_resolved_pct`, `models`, `framework_identities`,
  `facet_schema`, each catalogue's `rules_used`) is recomputed with U3's builders and compared; a sealed raw object
  whose listed digest matched is not read twice (its address is compared with that digest); member objects are always
  read (CRC-32).
- **Catalogue authority** is `corpus/authority.py` (`rules.mismatch` failed, `rules.unavailable` unverified). It also
  fixes U2's `rules/` check for sealed sources, which read the sealed semantics-profile file names and
  `corpus.rules.toml` as unshipped (false `rules.unavailable` notices in `recompute` of a sealed corpus).
- **`rederive`** is U2's `Derivation` run as `recompute --dry-run` into a private scratch tree (link-raw, no reuse
  cache), with the re-map's import pipeline injected (`corpus.verify.ImportHooks`; `adapters.runner` is L6).
  `--sample` restricts the stored-raw input tree to the sampled executions' inputs (`StoredRawTree.restrict`) and the
  comparison to the sample (`Derivation(scope=...)`); the corpus-level files are then not compared (notice). A
  `changed_explained` output (a declared version differs from the package's) is `unverified`: identity is not shown.
- **Sampling** (`--sample N --seed S`): ids ordered by `sha256("agentprov-sample/1\n" + S + "\n" + ex)`, first N taken
  (seeded, uniform, without replacement, independent of Python's `random` and of the hash seed). Per-execution checks and
  `rederive` use it; corpus-level checks always run in full.
- **Working trees** have no `checksums.sha256`: `checksums.absent` and closed-world findings are `unverified` (sealing
  refuses a tree that is not closed-world). Tombstoned objects (`raw/tombstones.jsonl`) are `tombstoned` with reason and
  date; checks that need their bytes are skipped.
- **`validate --corpus`** (`corpus/validation.py`) re-runs tiers `aer`, `sem`, `prov` (tier-4 checks other than
  `pv.linkage.*`) and `linkage` (`pv.linkage.*`) over the stored outputs, read-only for working corpora too (N.2.5(4)
  would write `validation/` into a working corpus; phase 11 keeps every consumer read-only and `derive` is the writer of
  that stage). Rows have the `validation/results.jsonl` shape; with every default tier in the corpus's own mode they are
  compared with the stored rows (`results_reproduced` / `results_differ`); the report (`--report PATH` outside the
  corpus, exit 4 inside; `-` for stdout) is `agentprov-validation-report/0.1` with the D-40 `ValidationSummary`.
  `--strict`/`--release` run the validators in release mode; `shacl` is not built (skipped, fails under strict) and
  `regression` is not applicable outside `adprov-v1`. `--jobs` is accepted; validation runs in the CLI process.

## Rejected alternatives

- **Extracting to a temporary directory and verifying the tree.** Forbidden (H.10.3(1), G.3.5): a hostile deposit could
  plant links or names that a tree walk then follows, and extraction writes untrusted bytes to disk.
- **A new T1 job kind now.** Ownership: `io/workers.py` and `worker.py` are phase 12's.
- **Trusting `DEPOSIT-MANIFEST.json` for the closed world.** It is inside the deposit; the corpus's own
  `checksums.sha256` (and the published root digest, D-39) are the authority, the deposit manifest is checked against them.
- **Failing a lone meta archive outright.** It is a useful partial check (manifest, checksums of what it holds); what it
  cannot show is reported unverified, never passed, and release mode fails it.
- **Running `rederive` on a deposit by streaming raw members into a scratch store.** That is extraction by another name.
