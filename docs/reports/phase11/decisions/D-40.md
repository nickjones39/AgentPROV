# D-40: the corpus `ValidationSummary`: mode, per-check version and tier, tier results, `linkage_resolved_pct` (phase 11, U3)

Status: implemented on branch `phase-11-u3` (U3), for consolidation into DECISIONS.md by the orchestrator. U4 makes
`validate --corpus` produce the same fields for every tier.
Code: `src/agentprov/corpus/manifest.py` (`validation_summary`, `linkage_resolved_pct`, `VALIDATION`). Tests:
`tests/unit/corpus/test_manifest_builders.py`, `tests/unit/corpus/test_package.py`.

## Decision

`corpus.json.validation` (H.2.12) is computed at sealing from `validation/summary.json`, `validation/results.jsonl` and
the `validation` stage of `derivation.json`:

```json
{"mode": "strict" | "dev",
 "checks": [{"id", "version", "tier", "pass", "fail", "skipped", "not_applicable"}],
 "tiers": [{"tier", "checks", "pass", "fail", "skipped", "not_applicable", "executions", "executions_passed"}],
 "linkage": {"spec": "agentprov-prov/0.1", "applicable": int, "resolved": int},
 "linkage_resolved_pct": {"$dec": "100.00"} | null,
 "libraries": {name: version}}
```

1. **`mode`**: `strict` when the validation stage ran in release mode (`mode: "release"` in `derivation.json`), else
   `dev`. `package` refuses a corpus whose validation did not run strict (exit 4), and a sealed manifest in strict mode
   has `skipped == 0` for every check (H.2.12; a skipped check never counts as passed).
2. **Per-check `version` and `tier`**: `aer.validator` is tier 2 at `aer/0.1`; a SEM check `<profile>@<n>:<id>` is tier 3
   at its profile (`agentdojo.suites@1`); every other check (`PV-NE-*`, `pv.*`) is tier 4 at the recorded PROV spec
   (`tier4:<spec>` of the stage, `agentprov-prov/0.1`).
3. **Tier results** (`tiers`): per tier, the number of checks, the summed check results, the executions with a result row
   (`executions`) and the executions whose every check of that tier is `pass` or `not_applicable`
   (`executions_passed`). These are the per-corpus tier pass figures the manuscript reads (`<src>/tier2_aer_pass`,
   `<src>/tier4_prov_pass`, `tab:validation`).
4. **`linkage_resolved_pct`** (claim `c1-linkage`, O_manuscript C1: `linkage_resolved_pct == 100.0` for every corpus,
   read from the corpus `validation/`). Over the rows of `validation/results.jsonl`, with `L(e)` the statuses of the
   execution's evidence-linkage checks (ids `pv.linkage.*`, D8 tier 4):
   - `applicable` = the number of executions with at least one status in `L(e)` other than `not_applicable`;
   - `resolved` = the number of applicable executions with every status in `L(e)` equal to `pass` or `not_applicable`
     (a `fail` or a `skipped` linkage check never resolves);
   - `linkage_resolved_pct = floor(10000 * resolved / applicable) / 100`, written with two decimals as the corpus-layer
     decimal `{"$dec": "<pct>"}` (corpus JSON holds no floating-point number, H.1.4(3); D-34), and `null` when
     `applicable == 0`. Flooring makes `"100.00"` exact: it is written only when every applicable execution resolves
     (99.996 % is `"99.99"`, never rounded up).
   The phase-10 corpora give `"100.00"` (e.g. Mandate 396/396, AgentHarm 1,056/1,056).
5. **`libraries`**: the stage's serialiser and validator versions (sorted).

## Why

The paper's C1 claim and its validation table must be read from the sealed corpus, not re-computed by the paper
pipeline; the tier and version fields make each count attributable to a check implementation (H.2.12; D8). Floats are
forbidden in the corpus layer, so the percentage is a decimal string that compares exactly.

## Rejected

- A float `linkage_resolved_pct` (breaks H.1.4(3) and the cross-serialiser stability it protects).
- Rounding to nearest (a 99.996 % corpus would read as 100.00 and pass `c1-linkage`).
- Counting check results instead of executions for the percentage (one execution with several failing linkage checks
  would weigh more than one).
