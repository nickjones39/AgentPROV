# D-30: `derive` and `recompute` live in `corpus/`, reuse the T1 job kind `prov`, re-map through `import_source`, and always write a new corpus (phase 11, U2)

Status: implemented on branch `phase-11-u2` (U2), for consolidation into DECISIONS.md by the orchestrator.
Code: `src/agentprov/corpus/derive.py`, `src/agentprov/corpus/rawtree.py`, `src/agentprov/cli/derive.py`.
Tests: `tests/unit/corpus/test_derive.py`, `tests/unit/corpus/test_derive_definitions.py`, `tests/unit/corpus/test_rawtree.py`.

## Decision

1. **Where.** The engine is `agentprov.corpus.derive` (L5). It never imports `adapters.runner` or
   `adapters.registry` (L6), and it imports no other `adapters` module either. What it needs from the adapter layer is
   injected by the CLI (M.5.2(1)): `Catalogues.source_profile_sha256(id, version)` and `Catalogues.semantics(ref)`
   (`SemanticsInfo`: digest, rules, family). The CLI module `agentprov.cli.derive` registers `derive` and `recompute`.
2. **Never in place.** Both commands read `--corpus SRC` (sealed, working or `.partial`) through `CorpusReader` and
   write `NEW.partial` (`--out NEW`). `NEW` must not exist, must be disjoint from `SRC` (both directions, including
   `SRC.partial`) and outside every sealed corpus; the `CorpusWriter` adds the git work-tree guard (G3) and the lock
   (G6). `--dry-run` builds into a private temporary directory that is removed afterwards (the importer's dry-run
   precedent), so it derives, validates and compares exactly what `--out` would (N.1.6(3)) and writes nothing next to
   the source or the output. Tests wrap every command in `testing.fs_guard.unchanged(SRC)`.
3. **Stages.** `--stages` names `expand,aer,sem,prov,validation,views`; `compat` is requested with `--prov-spec
   adprov-v2.3-compat` (D-37).
   - *Re-map* (`expand` or `aer` requested): `StoredRawTree` yields one candidate per non-member origin row of the
     source (label = git `origin.path`, or a `corpus` origin's path without the leaf of the snapshot pin's `tree`;
     sorted by label bytes), reads every object from the source store with a digest check, and gives the recorded
     origin, so the importer runs with `pin_check=None` and no network. The CLI calls the public
     `adapters.runner.importer.import_source(...)` with the values recorded in the source manifest and
     `derivation.json` (profile, part, snapshot, corpus id, `until`, semantics, mode, pin, selection filters, limit,
     limit overrides). Every downstream layer is recomputed with it. Register rows the re-map cannot reproduce
     (path subjects whose file was never stored: profile excludes, files the pin did not vouch for) are carried.
   - *Re-derive* (`sem`/`prov`/`validation`): the stored AER is copied unchanged after its seal is re-verified and its
     execution digest checked against the index; the AER validator runs in the parent (as in the importer); SEM, PROV
     and tiers 3-4 run as the existing T1 job kind `prov` (`adapters/runner/provjob.py`), submitted **by name** in
     batches over `WorkerPool`, consumed in index order, overlapped with the next batch. The three stages form one job,
     so asking for any of them recomputes the ones the source has. No job kind was added to `io/workers.py`.
   - `views` (`transcript-v1`) and `compat` are computed in the parent from the AER; every layer not recomputed is
     carried byte for byte.
4. **Re-implemented, pinned.** The `sem`, `prov` and `validation` stage definitions, `code_sha256` and the importer's
   `finish()` logic (validation rows, register details, verdicts) are re-implemented in `corpus/derive.py`; the B2
   completeness rule is `corpus.facets.completeness_of` (U1). `test_derive_definitions.py` pins the definitions and
   `code_sha256` equal to `importer._Pipeline.stage_definitions` and `importer.code_sha256`; the zero-difference tests
   pin the outputs.
5. **Documents.** The index is rebuilt with full H.3.1 rows (`facet_members`; a row stays a working row only when its
   execution has no `sem`, `prov` or `validation` stage, e.g. no semantics profile applies). `derivation.json` holds the
   recomputed stage definitions (from this run, or as the importer wrote them for a re-map) and keeps the carried ones;
   `views` and `compat` get their own stage entries. The working `corpus.json` is the source manifest without its
   sealed-only members, with recomputed counts, `prov_specs`, `oracle_specs`, a fresh `producer` block and
   `derived_from: {command, corpus_id, corpus_version|null, manifest_sha256, recomputed, root_digest|null, state}`.
   `command` and `recomputed` are additions to the PLAN shape: they identify the derivation for resume (item 7) and
   record what the new version recomputed.
6. **Comparison and classification** (H.8.4). Per execution, by bytes and digests only: AER bytes and execution digest,
   SEM digest per profile, PROV file sha256 per spec, validation-row JCS digest, view bytes. A changed output is
   `changed_explained` when the *declared identity* of its stage or of a stage upstream of it (`expand` → `aer` →
   `sem` → `prov` → `validation`; `aer` → `views` → `compat`) differs between the two `derivation.json` files. The
   declared identity is the stage definition minus `fn_digest`, `engine_code_sha256` and `adapter_code_sha256`, and
   minus the digests that sit beside an integer version (`aer` `profile_sha256` and `rules_sha256`, the digest values
   of `sem` `profiles`): under D-31 a content change needs a version bump, so a digest change at the same version is
   unexplained (and reported as `rules.mismatch`). The `prov` stage's `rules_sha256` stays declared, because the
   source records no integer version of the `aprov` catalogue. Library versions and the engine version string are
   declared; the interpreter stays outside (H.8.2(1)). Otherwise a changed output is `unexplained_change` (exit 1).
   `failed`: a stage newly failed or the source execution could not be read; `unverified`: the AER names a catalogue
   version the package does not ship. A code-digest-only change with identical outputs passes, with a notice.
   `index_refreshed` counts rows whose members outside the outputs differ (completeness, status, issues, ...); a
   working row becoming a full row is not a refresh. `raw/origins.jsonl`, `raw/members.jsonl` and `register.jsonl` are
   compared too; an unexplained difference there exits 1 (HL-T14). `--show-diff N` prints, for N changed executions,
   the first differing line of each changed file (JSON documents in a sorted indented rendering) and the PROV semantic
   diff (`prov.diff.diff_documents`), every line escaped.
7. **Inputs first and resume.** Before `NEW.partial` exists every listed raw object is re-hashed (`raw.digest.mismatch`,
   exit 1) and the recorded catalogue/profile digests are compared with the package (`rules.mismatch`,
   `rules.unavailable`; also against a sealed corpus's `rules/` copy, which is a record, never used). The first file
   written is the working `corpus.json` with `derived_from`. A later run with the same `derived_from` resumes: an
   execution whose index row records the same sealed AER is reused (D.2.9: keyed on the AER, never on file existence);
   a different `derived_from` is refused (exit 4). After a re-map the importer's manifest is re-stamped with
   `derived_from`, so an interrupted re-map is resumable too.
8. **`derive` versus `recompute`.** `recompute` re-runs the requested stages (default: every stage the source has,
   from raw) and compares. `derive` adds missing layers (`sem,prov,validation` when absent, `views`, `compat`) and
   carries present ones; a requested present layer whose package definition has another declared identity is refused
   (exit 4, N.2.3(4)). `derive` cannot re-map. `derive --trig DIR` writes TriG (E.5.4, `prov/serialise/trig.py`) for
   `NEW` (with `--out`) or for `SRC` (alone, which may then be sealed) into a directory outside every corpus, with a
   `trig.sha256` listing whose digest is reported with the `prov`/`rdflib` versions.

9. **Re-map then re-derive.** A re-map calls `import_source(..., until="aer")`: the importer stores, expands, maps,
   seals and runs the AER validator; SEM, PROV and validation then follow in `corpus.derive` over the AERs the
   importer wrote, exactly as in a re-derive (same job kind, same stage definitions, same register details). This is
   what lets a re-map reuse the outputs of every execution whose AER did not change (item 10). The result equals the
   importer's own `until="validation"` run byte for byte (pinned by the re-map tests and by the real-corpus runs of
   `derive-timings.md`).
10. **Reuse cache.** For each execution, the source's SEM, PROV and validation outputs (files, validation row, and the
    `sem`/`prov`/`validate` register rows) are carried instead of recomputed when the *reuse key* is unchanged, which
    is exactly the tuple on which those outputs depend:
    - the execution's sealed AER is the source's (same execution digest);
    - the `sem`, `prov` and `validation` stage definitions of this build have the source's `fn_digest` (engine and spec
      versions, code digests, semantics profiles and their digests, `aprov` catalogue digest, options, mode, checks,
      serialiser and validator library versions);
    - the interpreter (`python`) and the core lockfile digest equal the source's `derivation.json`;
    - every rule catalogue `(ns, version)` the AER header declares has, in this package, the digest the source recorded
      (`aer.rules_sha256`), and the source profile the header declares has the package digest the source recorded;
    - the source row has every output this run produces.

    The key is content-addressed only: no time, size or mtime enters it. `recompute --out` and `derive --out` reuse by
    default; `--no-reuse` forces a full recompute; `recompute --dry-run` never reuses, because it is the check, and a
    `--no-reuse` run is the proof that a reusing run gave the same bytes (`test_the_reuse_cache_gives_the_bytes_of_a_full_
    recompute`: identical trees for reuse and no reuse, `--jobs 1` and `4`, both for a re-derive and a re-map). The run
    is recorded in `derivation.json` as `"reuse": {"enabled": true, "reused": n, "recomputed": m,
    "recomputed_executions": [sorted ids]}` (or `{"enabled": false}`); every execution not listed was carried. (The
    list covers the invocation that finished the corpus; executions completed by an interrupted earlier invocation are
    neither listed nor recomputed again.) The key is coarse by design: a new semantics profile or catalogue version used
    by every execution changes a stage `fn_digest` and recomputes every execution, because which executions a rule change
    affects cannot be known without recomputing them. A re-map recomputes exactly the executions whose AER changed,
    which is what the AER-level items of the regeneration batch need. Reused outputs are read through `CorpusReader`,
    so they are checked against the source index (D9 chain) as they are copied; reuse cannot detect a source whose files
    and index were changed consistently, which is what `recompute --dry-run` is for.

## Why

- Layering: `corpus/` sits below `adapters.runner`; the derive logic needs the corpus model (reader, writer, index,
  facets) and the `prov` job, but must not pull the adapter registry into L5 (M.5.2(1), (4)).
- One pipeline: reusing the `prov` job kind and `import_source` means a re-derived or re-mapped execution is computed by
  exactly the code that imports it, so a recompute of an unchanged corpus is byte-identical (Q.14) and an adapter fix
  can be applied to an existing corpus without the network (regen-batch.md).
- Never in place keeps every sealed and working corpus immutable and makes a recompute transactional (RPR-3): an
  interruption leaves the source untouched and the output resumable.

## Rejected alternatives

- **`corpus.derive` importing `adapters.runner`** (or `adapters.profiles` directly): an upward or near-upward import
  that would couple L5 to the registry; injection is the rule M.5.2(1) names.
- **A new job kind** (`derive`) in `io/workers.py`: unnecessary; `prov` already takes a sealed AER and returns SEM,
  PROV and the validation frames.
- **Writing into the source when nothing changes** (the baseline's in-place recompute): rule 4; it also made the
  baseline non-transactional (R4).
- **Comparing parsed documents** (`old == new`): misses `true`→`1`→`1.0` and serialiser drift (baseline R2).
- **Counting a code-digest change as a version change**: it would hide unintended output changes behind refactors
  (H.8.4(2)); conversely, catalogue digests beside an integer version are not declared versions (D-31).
- **A dry run that keeps everything in memory**: it could not compare files the importer writes, and it would be a
  second code path; the private temporary tree is the importer's own dry-run mechanism.
- **Resuming on file existence**: the baseline's R6 defect; resume is keyed on the sealed AER recorded in the index.
- **A finer reuse key** (per rule that fired): which executions a rule or profile change affects is only known after
  recomputing them; a wrong guess would silently keep stale provenance.
- **Reuse in `recompute --dry-run`**: the check would then compare the source with a copy of itself.
- **A reuse key with timestamps or file sizes**: not content-addressed; a touched file would change it, a rewritten
  file of the same size would not.
- **Threads or free-threaded Python for speed**: the rlimited T1 worker processes are a security boundary; the measured
  hot spot (tier-4 round trip) is recorded in `derive-timings.md` for the `validate/` owner instead.
