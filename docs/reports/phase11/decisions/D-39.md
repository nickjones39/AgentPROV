# D-39: `verify --root-digest sha256:…` (phase 11, U4)

Status: implemented on branch `phase-11-u4` (U4), for consolidation into DECISIONS.md by the orchestrator.
Code: `src/agentprov/corpus/verify.py` (`root_digests`), `src/agentprov/release/verify.py`, `src/agentprov/cli/verify.py`.
Tests: `tests/corpus/test_tamper.py` (`test_regenerated_checksums_over_a_datasheet_edit_are_detected_only_by_the_root_digest`,
`test_manifest_or_index_edited`, `test_regenerated_checksums_over_a_tampered_prov_file_fail_the_chain`),
`tests/corpus/test_deposit_verify.py` (`test_a_consistent_forgery_is_detected_only_by_the_published_root_digest`,
`test_a_lone_meta_archive`), `tests/corpus/test_verify.py`.

## Decision

1. **Option.** `agentprov verify --root-digest sha256:<64 lower-case hex>` (repeatable; API `root_digests=`). The value
   is a root digest published **outside** the corpus (H.5.4: the corpus tag annotation, the paper, the deposit record).
   It never comes from inside the corpus or the deposit.
2. **Check.** The root digest is `"sha256:" + sha256(bytes of checksums.sha256)` (H.5.4). In tree mode each given digest
   must equal it; in archive mode each given digest must equal the computed root digest of one corpus of the deposit
   (corpora without a given digest are checked against the deposit manifest only). A difference is
   `root_digest.mismatch` (failed, exit 1); a tree without `checksums.sha256` (a working tree) cannot match and gives
   `root_digest.unverifiable` (failed). The check runs at every level, `checksums` included.
3. **Required in release mode when nothing else anchors the digest.** `verify --release` in tree mode, and on a lone meta
   archive, needs at least one `--root-digest` (exit 2 otherwise): every other check can be satisfied by an attacker who
   regenerates `checksums.sha256` over files no digest chain covers (`DATASHEET.md`, `CHANGELOG.md`, `LICENSES/**`, a
   `rules/` copy the manifest does not name). A deposit directory is anchored by its `DEPOSIT-MANIFEST.json` (root
   digest per corpus, archive sha256/md5), so `--root-digest` is optional there; giving it is still the only defence
   against a deposit forged consistently end to end (test: a corpus edited, its checksums regenerated, a deposit built
   from it, passes every other check).
   **Amended by D-620 (2026-10-22, ultra seal-release #8):** `DEPOSIT-MANIFEST.json` lies in the same untrusted
   directory as the archives it describes, so it anchors nothing. `verify --release` on a deposit directory now needs
   `--root-digest` as well (exit 2 before anything is read); without `--release` the option stays optional everywhere.
4. **Format and display.** The value is validated before anything is read (`sha256:` plus 64 lower-case hex digits;
   exit 2). The computed root digest is printed after every tree-mode or archive-mode run (`root digest sha256:…`) so that
   a user can publish or compare it; it is never written into the corpus (H.5.4).

## Why

H.5.4 makes the root digest the fingerprint of a release tree and keeps it outside the tree, because a bundle cannot
contain its own hash. K.12.5's row "`checksums.sha256` regenerated by the attacker" is detected by the AER seal → SEM →
PROV chain only when the forged file is one the chain covers; for the rest, the published root digest is the only
evidence. Making it mandatory for release-mode tree verification turns that from advice into a gate.

## Rejected alternatives

- **Reading the expected root digest from a file inside the corpus or deposit.** Circular: whoever can regenerate the
  checksums can regenerate that file.
- **Requiring `--root-digest` in dev mode too.** Dev-mode verification of a working or local corpus has nothing
  published to compare with; the dev summary prints the computed digest instead.
- **Accepting a bare hex digest.** The `sha256:` prefix is the corpus-layer digest form (H.2.11) and keeps the option
  open to other algorithms without ambiguity.
- **Treating a mismatch as `unverified`.** A published digest that differs is evidence of a different tree: it fails.
