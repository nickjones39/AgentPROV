# D-37: compat outputs through `derive --prov-spec adprov-v2.3-compat`, the lazy loader, `oracle_specs`, row `oracles` and the R-55 notice (phase 11, U2)

Status: implemented on branch `phase-11-u2` (U2); user ruling 2026-10-11 (the released adprov-v1 carries the compat
graphs, no other corpus does); for consolidation into DECISIONS.md.
Code: `prov/specs.py` (`load_compat_spec`, `compat_notice`, `COMPAT_SPEC_ID`, `REGRESSION_ORACLE`),
`corpus/derive.py` (`Derivation._views_and_compat`, `compat_stage_definition`), `cli/derive.py`.
Tests: `test_derive_writes_compat_graphs_flagged_as_regression_oracle`, `test_compat_is_not_applicable_outside_the_view_families`.

## Decision

1. **How compat output is produced.** `derive --corpus SRC --out NEW --prov-spec adprov-v2.3-compat` renders the
   transcript/v1 view of each AER in the parent (`views.transcript_v1.render` for `adprov.transcript_v1` AERs,
   `render_converted` for `agentdojo.tracelogger` AERs; C.15.3, E.8.2; nothing is read from raw, AD-02), builds the
   graph with the frozen oracle (`CompatSpec.build`, default flags) and stores `CompatSpec.serialise` bytes at
   `prov/adprov-v2.3-compat/<ss>/<ex>.prov.json`. For every other adapter the stage is `not_applicable` and nothing is
   written. A view or oracle failure is `prov.failed` (detail `adprov-v2.3-compat: <reason>`), never a dropped row.
   `recompute` re-derives existing compat output (and compares it); it cannot add it.
2. **Lazy loader.** `agentprov.prov.specs.load_compat_spec()` is the only importer of `agentprov.prov.compat` outside
   `migration` and the tests (M.5.2(3)), and only when the spec is requested; `corpus.derive` calls it, never the compat
   package directly.
3. **Flags.** Each row with compat output has `oracles: {"adprov-v2.3-compat": {"gate_report": null, "status":
   "apv:RegressionOracle"}}` (H.3.1, `facets.oracles_for`); the working manifest has `prov_specs` (with the compat spec)
   and `oracle_specs: [{"gate_report": null, "spec": "adprov-v2.3-compat", "status": "apv:RegressionOracle"}]` (H.2.2;
   `[]` when none). `gate_report` stays `null` until a gate-B report is attached (U3/U4 may fill it).
4. **Notice.** Whenever compat output is written or carried/loaded, the CLI prints the oracle's `NOTICE` (R-55, Q.30)
   on stderr and puts it in the summary's `notices`.
5. **Function identity.** A `compat` stage entry in `derivation.json`
   (`{stage: compat, fn: provenance, spec, status, view, engine, engine_code_sha256 over prov/compat and views}`), and a
   `views` entry when the views are written. These are separate from the `prov` stage, so the importer's resume check
   (keyed by stage name) is unaffected.
6. **Which corpora.** Per the user's ruling only the released `adprov-v1` corpus is derived with compat graphs; the
   mechanism works on any AgentDojo-family corpus, but no other corpus is built with it.

## Why

The compat graphs are the regression oracle of the migration (gate B): regenerated from the AER through the view they
must equal the baseline bytes, which the test checks for every golden release pair. Producing them as an explicit,
flagged layer of a new version keeps them out of the default derivation and out of every other corpus, and the notice
and flags stop a reader from mistaking them for the recommended semantics (E.8.1).

## Rejected alternatives

- **Compat during `import`** (`--prov-spec` on import): rejected in phase 6 and kept rejected; it would put the oracle
  into the default pipeline.
- **Compat inside the T1 `prov` job**: the job kind is `agentprov-prov/0.1` only; adding the oracle there would load the
  quarantined package in every worker.
- **Importing `agentprov.prov.compat` from `corpus/`**: breaks the quarantine of M.5.2(3).
- **Compat for every AgentDojo-family corpus**: the user ruled it is shipped with adprov-v1 only.
